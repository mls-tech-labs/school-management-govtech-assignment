# Feature Specification: Teachers & Classes — UPDATE / DELETE Mutations

**Feature Branch**: `006-teachers-classes-mutations`
**Created**: 2026-06-22
**Status**: Draft (Stage 3)
**Input**: User description: "Stage 3 — introduce UPDATE and DELETE operations on Teachers and Classes (per constitution v2.5.0 Principle X). Includes: PUT/DELETE endpoints on /api/v1.0/teachers/[ulid] and /api/v1.0/classes/[ulid], referential integrity rule (DELETE-Teacher blocked when currently a form teacher, returns 409), idempotent DELETE-Class (second DELETE returns 404), idempotent UPDATE, restoration of the Singapore ^[89]\d{7}$ contact-number rule. UI: per-row ... clickable menu on Teachers and Classes lists with Edit/Delete options; Delete opens a confirmation modal."

## Clarifications

### Session 2026-06-22

- Q: Should the Edit form be a separate page (e.g., `/teachers/[ulid]/edit`) or an in-place modal/drawer on the list screen? → A: **Separate page** — `app/(authed)/teachers/[ulid]/edit/page.tsx` and `app/(authed)/classes/[ulid]/edit/page.tsx`. This mirrors the existing Add Teacher / Add Class pattern (Stage 1, `app/(authed)/teachers/new/page.tsx` and `app/(authed)/classes/new/page.tsx`) and reuses the same form components in "edit mode" gated by the presence of a path parameter. The submit handler swaps from POST to PUT depending on the mode. Rationale: zero new form components, zero new design tokens, follows the existing route convention, and keeps the per-row `...` menu's job narrow (open the edit page, not host a form).
- Q: Should the DELETE confirmation modal embed the entity's name in the copy, and what should the destructive button look like? → A: **Yes, embed the name** — the modal body reads `Delete teacher {name}? This action cannot be undone.` (and the class equivalent). The destructive button uses the project's existing Tailwind destructive-action token (red palette, defined in `tailwind.config.ts` per Principle VIII) — no new design tokens. The Cancel button uses the standard antd `Button` default style.
- Q: When DELETE-Teacher is blocked because the teacher is currently a form teacher (HTTP 409), how should the UI surface the affected classes? → A: **Display the affected class names in an antd error notification** (the same notification pattern used for the existing `409 Conflict` and `404 Not Found` paths on the Add forms) — the notification body lists the affected class names (e.g., "Assigned as form teacher of: Class 1A, Class 2B. Reassign or delete those classes first."). The wire envelope is `{ "error": "Teacher is assigned as form teacher of <n> class(es)", "details": { "classUlids": ["01H...", "01H..."], "classNames": ["Class 1A", "Class 2B"] } }` — the `details` block is an extension to the standard `{ "error": "..." }` envelope (per Principle VII — the `error` field stays canonical; `details` is an opt-in extension specific to the DELETE-Teacher 409 case). This matches the principle in `003-backend-api-db/spec.md` FR-013 that error responses carry a primary `error` string.
  **Superseded by Session 2026-06-22 (DELETE-Teacher 409 envelope — one-to-one simplification) below** — the DB's `UNIQUE INDEX uq_classes_form_teacher_id` constraint guarantees at most one affected class (N is always 0 or 1), so the array envelope (`classUlids[]` / `classNames[]`) and the plural error string (`<n> class(es)`) are over-spec'd. The new sub-session's Option B envelope (single object: `classUlid` + `className`, both singular; error string embeds the class name in double quotes) is the canonical rule.
- Q: Is the UPDATE idempotent in the strict sense (same body twice yields the same result with no side effects on the second call), or is it idempotent in the loose sense (retrying a timed-out PUT returns 200)? → A: **Strict HTTP-semantics idempotency** — applying the same `PUT` body twice yields the same row state with no side effects on the second call (audit columns `modified_at` / `modified_by` are updated by both calls, but the row's content is identical; `version` increments by exactly 1 per call). The 200 response body on the second call is identical to the first. No 409 conflict is raised for "no change detected" — UPDATE is unconditional, the same way POST is.

### Session 2026-06-22 (contact-number rule restoration)

- Q: Restore the Singapore `^[89]\d{7}$` rule that was relaxed to `^\d{8}$` in `001-teachers/spec.md` Clarifications Session 2026-06-21? → A: **Yes, restore `^[89]\d{7}$`** — the Singapore-mobile leading-digit assumption is reinstated on the Teacher `contactNumber` field. The Joi schema regex becomes `^[89]\d{7}$`; the corresponding unit tests are updated to cover the leading-digit rejection path (values starting with `0`, `1`, ..., `7`, `10`, etc. are rejected with HTTP `400` and a field-level `contactNumber` error). This is propagated by reference to `001-teachers/spec.md` FR-004 (the per-spec amendment is a Clarifications session in that spec; the implementation here uses the restored regex).

- Q3 (concurrent edit notification contract): when admin A submits an UPDATE that overwrites admin B's earlier UPDATE (different browser tab, same `ulid`), should the UI (a) silently accept the update (last-write-wins, no notification), (b) silent success + post-submit non-blocking warning toast, or (c) reject the second update with 409 on `version` mismatch? → A: **Option B — silent success + post-submit warning toast**. ## User Scenarios & Testing *(mandatory)*

### User Story 1 - Edit an Existing Teacher (Priority: P1)

An administrator clicks the per-row `...` menu on a teacher row in the Teachers list, selects **Edit**, and is taken to a pre-populated edit form. After changing one or more fields (name, subject, email, or contact number) and submitting, the teacher record is updated and the administrator is returned to the Teachers list which now shows the updated values.

**Why this priority**: Edit is the most common corrective action against a mis-entered or out-of-date record; without it, the only way to fix a typo is to delete the row and re-create it (which the form-teacher referential integrity rule may forbid). Edit is the read-write-update counterpart to the Stage 1 Create flow and is required for any admin tool that holds real data.

**Independent Test**: Can be fully tested by navigating to `/teachers`, clicking the `...` menu on a row, selecting Edit, modifying any subset of the four mutable fields (name, subject, email, contact number), submitting, and verifying the row reflects the new values and a `PUT /api/v1.0/teachers/[ulid]` call returned 200.

**Acceptance Scenarios**:

1. **Given** a teacher exists in the system, **When** the administrator clicks the per-row `...` menu on that teacher's row in the Teachers list, **Then** a small dropdown menu appears with **Edit** and **Delete** options.
2. **Given** the dropdown menu is open, **When** the administrator clicks **Edit**, **Then** the administrator is navigated to `/teachers/[ulid]/edit` which shows the existing Add Teacher form pre-populated with the teacher's current `name`, `subject`, `email`, and `contactNumber` values.
3. **Given** the administrator is on the Edit Teacher screen with a pre-populated form, **When** the administrator changes one or more fields and submits a valid form, **Then** the system records the update, the form-level submission succeeds, and the administrator is returned to the Teachers list which now shows the updated values.
4. **Given** the administrator is on the Edit Teacher screen, **When** the administrator submits a form with an invalid email, an invalid contact number (e.g., starting with `5` instead of `8` or `9`), a duplicate email belonging to a different teacher, or a reference to an unknown/inactive `subject.ulid`, **Then** the screen shows the corresponding field-level errors and the teacher is not updated.
5. **Given** the administrator is on the Edit Teacher screen and another administrator has already updated the same teacher (different browser tab), **When** the administrator submits their edit, **Then** the system accepts the second update (last-write-wins; PUT is idempotent in the strict sense — see Clarifications Session 2026-06-22, Q4 in the `/speckit-specify` pass). No 409 "stale version" conflict is raised; the audit columns record the most recent write. After the form returns to the Teachers list, the UI shows a non-blocking antd warning notification reading `Note: this record was edited by another administrator at HH:MM:SS — your changes are saved, but please verify.` (see Clarifications Session 2026-06-22, Q3 in the `/speckit-clarify` pass — `previousModifiedAt` differs from the form-load-time `modifiedAt`). The notification is informational only; the update has already been saved.

### User Story 2 - Delete an Existing Teacher (Priority: P1)

An administrator clicks the per-row `...` menu on a teacher row in the Teachers list, selects **Delete**, and is shown a confirmation modal embedding the teacher's name. After confirming, the teacher is deleted from the system (when permitted) and the Teachers list refreshes without the row. When the teacher is currently assigned as the form teacher of one or more classes, the delete is rejected with HTTP 409 Conflict and the administrator sees a notification naming the affected classes.

**Why this priority**: Delete is the corrective counterpart to Create. The form-teacher referential integrity rule is the single most important domain constraint Stage 3 introduces — without DELETE the database has no way to recover from bad data, and without the 409 guard the rule would silently leave classes with dangling references.

**Independent Test**: Can be fully tested by navigating to `/teachers`, clicking the `...` menu on a row, selecting Delete, confirming the modal, and verifying the row disappears from the list and a `DELETE /api/v1.0/teachers/[ulid]` call returned 200. The negative path is independently testable by deleting a teacher who is currently a form teacher of any class and verifying a 409 with the `{ "error": "...", "details": { "classNames": [...] } }` envelope is returned.

**Acceptance Scenarios**:

1. **Given** a teacher exists in the system and is NOT currently assigned as the form teacher of any class, **When** the administrator clicks the per-row `...` menu on that teacher's row, selects Delete, and confirms the modal, **Then** the system deletes the teacher and the Teachers list refreshes without the row.
2. **Given** the administrator has clicked Delete on a teacher, **When** the confirmation modal opens, **Then** the modal body reads `Delete teacher {name}? This action cannot be undone.` with **Cancel** and **Delete** (destructive) buttons. Clicking **Cancel** closes the modal without making the API call.
3. **Given** a teacher IS currently assigned as the form teacher of one class (the only cardinality possible, per `UNIQUE INDEX uq_classes_form_teacher_id`), **When** the administrator clicks Delete on that teacher and confirms the modal, **Then** the API returns HTTP 409 Conflict with `{ "error": "Teacher is assigned as form teacher of class \"<className>\". Reassign or delete that class first.", "details": { "classUlid": "<classUlid>", "className": "<className>" } }` (per FR-009, Clarifications Session 2026-06-22 (DELETE-Teacher 409 envelope — one-to-one simplification)), the modal closes, and an antd error notification appears whose body reads `Assigned as form teacher of: <className>. Reassign or delete that class first.` (e.g., `"Assigned as form teacher of: Class 1A. Reassign or delete that class first."`). The `details.classUlid` is preserved in the wire envelope for programmatic consumers (deep-link to `/classes/[ulid]/edit`). The previous array envelope (`details.classUlids[]`, `details.classNames[]`) and the Q5 N > 5 truncation logic are superseded.
4. **Given** a teacher was already deleted in another browser tab (race), **When** the administrator clicks Delete on that same teacher and confirms, **Then** the API returns HTTP 404 Not Found with `{ "error": "Teacher not found" }`, the modal closes, the Teachers list refreshes (the row was already gone), and no error notification is shown (404 on DELETE is informational, not an error).
5. **Given** the network is unavailable while confirming the Delete modal, **When** the API call fails, **Then** the modal stays open (or re-opens if the request fired asynchronously), and an antd error notification shows a meaningful network-failure message. The teacher is NOT deleted.

### User Story 3 - Edit an Existing Class (Priority: P1)

An administrator clicks the per-row `...` menu on a class row in the Classes list, selects **Edit**, and is taken to a pre-populated edit form. After changing one or more fields (name, level, or form teacher) and submitting, the class record is updated and the administrator is returned to the Classes list which now shows the updated values.

**Why this priority**: Edit is the corrective counterpart to Stage 1's Create Class flow. The form-teacher uniqueness invariant (a teacher can be the form teacher of at most one class) MUST be re-checked on UPDATE — this is the canonical reason Principle X.3 exists.

**Independent Test**: Can be fully tested by navigating to `/classes`, clicking the `...` menu on a row, selecting Edit, modifying the form teacher to a different registered teacher (one who is NOT already a form teacher of any class), submitting, and verifying the row reflects the new form teacher and a `PUT /api/v1.0/classes/[ulid]` call returned 200.

**Acceptance Scenarios**:

1. **Given** a class exists in the system, **When** the administrator clicks the per-row `...` menu on that class's row in the Classes list, **Then** a small dropdown menu appears with **Edit** and **Delete** options (same shape as the Teachers-list menu).
2. **Given** the dropdown menu is open, **When** the administrator clicks **Edit**, **Then** the administrator is navigated to `/classes/[ulid]/edit` which shows the existing Add Class form pre-populated with the class's current `name`, `level`, and `formTeacher` (resolved from the `formTeacher.ulid`).
3. **Given** the administrator is on the Edit Class screen, **When** the administrator changes the form teacher to a different registered teacher who is NOT already the form teacher of any other class, **Then** the system records the update and the Classes list refreshes with the new form teacher name.
4. **Given** the administrator is on the Edit Class screen, **When** the administrator changes the form teacher to a teacher who is ALREADY the form teacher of a DIFFERENT class, **Then** the API returns HTTP 409 Conflict with `{ "error": "Teacher is already assigned as form teacher of another class" }`, and the screen shows a field-level error on the Form Teacher control. The class is NOT updated.
5. **Given** the administrator is on the Edit Class screen, **When** the administrator changes the `name` to a value that matches another existing class's name, **Then** the API returns HTTP 409 Conflict with `{ "error": "Class name already in use" }` and the screen shows a field-level error on the Name control.
6. **Given** the administrator is on the Edit Class screen, **When** the administrator changes the `level.ulid` to an unknown or inactive level, **Then** the API returns HTTP 400 Bad Request and the screen shows a field-level error on the Level control.

### User Story 4 - Delete an Existing Class (Priority: P1)

An administrator clicks the per-row `...` menu on a class row in the Classes list, selects **Delete**, and is shown a confirmation modal embedding the class's name. After confirming, the class is deleted and the Classes list refreshes without the row. A second delete on the same `ulid` returns 404 silently.

**Why this priority**: Delete is the corrective counterpart to Stage 1's Create Class flow. The idempotency rule (Principle X.2 — second DELETE returns 404) is the design contract that lets the UI safely retry deletes across flaky networks without surfacing 404 as an error.

**Independent Test**: Can be fully tested by navigating to `/classes`, clicking the `...` menu on a row, selecting Delete, confirming, and verifying the row disappears. The idempotency path is independently testable by clicking Delete on the same `ulid` a second time and verifying the list refreshes silently (no error notification, no modal error state).

**Acceptance Scenarios**:

1. **Given** a class exists in the system, **When** the administrator clicks the per-row `...` menu on that class's row, selects Delete, and confirms the modal, **Then** the system deletes the class and the Classes list refreshes without the row.
2. **Given** the administrator has clicked Delete on a class, **When** the confirmation modal opens, **Then** the modal body reads `Delete class {name}? This action cannot be undone.` with **Cancel** and **Delete** (destructive) buttons.
3. **Given** a class was already deleted in another browser tab (race) or via a previous attempt, **When** the administrator clicks Delete on that same class and confirms, **Then** the API returns HTTP 404 Not Found with `{ "error": "Class not found" }`, the modal closes, the Classes list refreshes, and no error notification is shown (404 on DELETE is informational, not an error — see Principle X.2).
4. **Given** the network is unavailable while confirming the Delete modal, **When** the API call fails, **Then** the modal stays open, and an antd error notification shows a meaningful network-failure message. The class is NOT deleted.
5. **Given** a class is currently deleted, **When** the Classes list refreshes, **Then** the class no longer appears in the list — and any teacher who was the deleted class's form teacher is now eligible to be the form teacher of a new class (the form-teacher uniqueness invariant is freed by the class delete).

### Edge Cases

- **What happens when the administrator opens the Edit Teacher / Edit Class page directly via URL on a `ulid` that does not exist?** The page's React Server Component shell calls the new `GET /api/v1.0/teachers/[ulid]` (or `GET /api/v1.0/classes/[ulid]`) endpoint (per FR-002 / FR-003 above and the constitution v2.6.0 amendment); if the `ulid` does not match any registered record, the endpoint returns `404 Not Found` with `{ "error": "Teacher not found" }` (or `{ "error": "Class not found" }`), and the RSC shell calls Next.js `redirect("/teachers")` (or `redirect("/classes")`) with a flash message rendered as an antd warning notification ("Teacher not found" / "Class not found") on the list page. No edit form is shown. (This case is now resolved by the new single-resource GET endpoints — the previous `TODO(SINGLE_RESOURCE_FETCH_OUT_OF_SCOPE)` marker is REMOVED; the architectural question is resolved by the constitution v2.6.0 amendment's authorisation of the new GET endpoints, not by an RSC + typeORM fallback owned by this spec.)
- **What happens when the administrator submits an Edit Teacher form with a `subject.ulid` that has been deactivated in another tab?** The route handler re-validates `subject.ulid` against the `subjects` table's `active` column; an inactive subject returns HTTP 400 Bad Request and the screen shows a field-level error. The teacher is NOT updated.
- **What happens when the administrator submits an Edit Class form with the SAME form teacher the class already has?** The route handler checks form-teacher uniqueness against `classes.form_teacher_id`; the same teacher on the same class is permitted (no `form_teacher_id` change → no violation). The update succeeds with 200.
- **What happens when two administrators delete the same teacher at the same time?** The first request gets the row-level lock, deletes, returns 200. The second request finds no row, returns 404 with `{ "error": "Teacher not found" }`. The UI on the second tab refreshes the list silently. No race-condition error surfaces to the user.
- **What happens when the administrator types a `contactNumber` that does NOT start with `8` or `9` (e.g., `12345678`)?** The Joi regex `^[89]\d{7}$` rejects the value; the field-level error reads `Contact number must start with 8 or 9 and be 8 digits.` (the same message format used by the existing Add Teacher form). HTTP 400.
- **What happens when the CSRF token has expired between page load and submit?** The double-submit-cookie middleware (per Principle IX.3, owned by `005-security-hardening`) rejects the request with HTTP 403 Forbidden. The UI re-fetches the CSRF token via `lib/security/csrf-client.ts → getCsrfToken()` and retries the mutation once. (Token refresh is owned by 005; the Stage 3 UI just calls the helper.)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001** (Stage 3 — UI menu): The system MUST display a per-row `...` button (right-aligned, in a dedicated actions column on the Teachers and Classes list tables) for every row. Clicking the `...` button MUST open a small dropdown menu (composed from the antd `Dropdown` primitive) with two menu items: **Edit** and **Delete**. The button MUST have an `aria-label` of `Row actions` as a low-cost screen-reader hint that is announced on mouse hover/focus regardless of keyboard-interaction support. **Keyboard accessibility (Tab to focus, Enter/Space to open, ArrowDown/Up to navigate, Enter to select, Escape to close) is NOT a Stage 3 requirement** — see Clarifications Q4 and the explicit Stage 3 Out of Scope entry in FR-015. Stage 3 ships mouse-only for the per-row menu and the Delete confirmation modal; keyboard interaction is a future-stage amendment.
- **FR-002** (Stage 3 — Edit Teacher page): The system MUST expose a page at `app/(authed)/teachers/[ulid]/edit/page.tsx` (routed at `/teachers/[ulid]/edit`) that reuses the existing Add Teacher form component in "edit mode" gated by the presence of the `ulid` path parameter. The page MUST be a React Server Component: its `page.tsx` calls the new `GET /api/v1.0/teachers/[ulid]` endpoint (per the constitution v2.6.0 amendment and FR-007b in `specs/001-teachers/spec.md` / FR-002 in `specs/003-backend-api-db/spec.md`) with the `ulid` path parameter and passes the matching record as a prop to the existing Add Teacher form component, pre-populated with the teacher's current `name`, `subject`, `email`, and `contactNumber` values. If the endpoint returns `404 Not Found` with `{ "error": "Teacher not found" }`, the RSC shell calls Next.js `redirect("/teachers")` and the destination list page renders an antd warning notification reading "Teacher not found" (see Edge Cases below). The page MUST render with a populated form on first paint (no client-side blank state during data population). On submit, the page MUST issue `PUT /api/v1.0/teachers/[ulid]` (not POST) with the form body. **Supersedes the prior Q2 (Option C — server-side RSC + typeORM fallback)** per the constitution v2.6.0 amendment; the new GET endpoint is the only data source for the Edit page.
- **FR-003** (Stage 3 — Edit Class page): Same as FR-002 for classes — `app/(authed)/classes/[ulid]/edit/page.tsx` is a React Server Component, calls the new `GET /api/v1.0/classes/[ulid]` endpoint (per the constitution v2.6.0 amendment and FR-007b in `specs/002-classes/spec.md` / FR-003 in `specs/003-backend-api-db/spec.md`) with the `ulid` path parameter, passes the matching class record (`name`, `level`, `formTeacher`) to the existing Add Class form component in edit mode, and issues `PUT /api/v1.0/classes/[ulid]` on submit. If the endpoint returns `404 Not Found` with `{ "error": "Class not found" }`, the RSC shell calls Next.js `redirect("/classes")` and the destination list page renders an antd warning notification reading "Class not found" (see Edge Cases below). **Supersedes the prior Q2 (Option C — server-side RSC + typeORM fallback)** per the constitution v2.6.0 amendment; the new GET endpoint is the only data source for the Edit page.
- **FR-004** (Stage 3 — DELETE confirmation modal): When the administrator clicks **Delete** in the per-row menu, the system MUST open an antd `Modal.confirm` whose body embeds the entity's name: `Delete teacher {name}? This action cannot be undone.` for teachers, `Delete class {name}? This action cannot be undone.` for classes. The modal MUST present **Cancel** (default-style button, no API call) and **Delete** (destructive-style button using the project's Tailwind destructive-action token). On **Delete** confirmation, the system MUST issue `DELETE /api/v1.0/teachers/[ulid]` or `DELETE /api/v1.0/classes/[ulid]` respectively.
- **FR-005** (Stage 3 — error notifications): On a 409 Conflict from DELETE-Teacher (because the teacher is currently a form teacher of exactly one class, per `UNIQUE INDEX uq_classes_form_teacher_id`), the system MUST close the modal and show an antd error notification whose body reads `Assigned as form teacher of: {className}. Reassign or delete that class first.` where `{className}` is the singular value of `details.className` (per Clarifications Session 2026-06-22 (DELETE-Teacher 409 envelope — one-to-one simplification) — supersedes the prior Q5 truncation logic which assumed N > 5 is reachable; N is always 0 or 1 under the UNIQUE constraint, so no truncation, no `… and N more` suffix, no comma-separated list). On a 409 Conflict from UPDATE-Teacher (duplicate email), UPDATE-Teacher (unknown/inactive subject), UPDATE-Class (duplicate name, form teacher collision, unknown/inactive level), the system MUST keep the form open and show a field-level error on the corresponding control. On a 500/503 from any Stage 3 endpoint, the system MUST show an antd error notification with the standard error envelope's `error` string.
- **FR-006** (Stage 3 — idempotent DELETE list refresh): On a successful 200 OK from DELETE-Teacher or DELETE-Class, OR a 404 Not Found from a second DELETE on the same `ulid`, the system MUST refresh the corresponding list view (no full-page reload — the existing client-side fetch pattern is reused). On 404 specifically, no error notification is shown (the row was already gone; the user's intent is satisfied).
- **FR-007** (Stage 3 — API: PUT teacher): The system MUST expose `PUT /api/v1.0/teachers/[ulid]` (per `003-backend-api-db/spec.md` FR-022 versioned prefix) that accepts the four mutable fields (`name`, `subject` as nested `{ ulid, name }`, `email`, `contactNumber`) in the request body and, on success, returns the updated teacher in the same shape as the corresponding GET entry, with HTTP 200 OK. The `ulid` is taken from the path parameter, not the body, and is immutable. The route MUST re-run every POST-side invariant (per Principle X.3): subject-active (FR-005a, 001-teachers), email-unique (FR-005, 001-teachers), and the contact-number rule (FR-013 of this spec). The email-uniqueness check MUST exclude the row being updated (i.e., the route queries `WHERE email = ? AND id != <teacher.id resolved from path ulid>`); submitting the teacher's current email as the new email is a valid no-op update that returns 200 OK with the row content unchanged (audit columns `modified_at` / `modified_by` / `version` are still incremented by exactly 1; see also Clarification Session 2026-06-22 Q4 on UPDATE idempotency semantics). On success, the 200 response body MUST additionally include the row's pre-update `modified_at` value (the `modified_at` immediately before the just-completed write) as a sibling field named `previousModifiedAt` — this enables the client-side concurrent-edit toast described in FR-016 and Clarifications Q3. On failure, the route returns the same JSON error envelope (`{ "error": "..." }`) and HTTP status code as the equivalent POST failure (`400` / `404` / `409`).
- **FR-008** (Stage 3 — API: PUT class): Same as FR-007 for classes — `PUT /api/v1.0/classes/[ulid]` accepts `name`, `level` as nested `{ ulid, name }`, `formTeacher` as nested `{ ulid, name }`, and re-runs every POST-side invariant: level-active (FR-005a, 002-classes), form-teacher-existence (FR-004, 002-classes), form-teacher-uniqueness against a DIFFERENT class (FR-005, 002-classes), and class-name-uniqueness (FR-005c, 002-classes).
- **FR-009** (Stage 3 — API: DELETE teacher): The system MUST expose `DELETE /api/v1.0/teachers/[ulid]` that performs a hard delete on the teacher. The route MUST first check whether the teacher is currently assigned as the form teacher of any class (a single query: `SELECT id, ulid, name FROM classes WHERE form_teacher_id = ?` — the `UNIQUE` index on `classes.form_teacher_id` guarantees at most one row is returned; the query is `O(log n)` against the index); if so, the route MUST reject with HTTP 409 Conflict and the envelope `{ "error": "Teacher is assigned as form teacher of class \"<className>\". Reassign or delete that class first.", "details": { "classUlid": "<classUlid>", "className": "<className>" } }` where `<classUlid>` and `<className>` are the single affected class's `ulid` and `name` (per Clarifications Session 2026-06-22 (DELETE-Teacher 409 envelope — one-to-one simplification) — supersedes Q3 array envelope and Q5 truncation logic). On success (teacher not a current form teacher), the route deletes the row and returns HTTP 200 OK with `{ "ulid": "<deleted-teacher-ulid>" }`. A second DELETE on the same `ulid` returns HTTP 404 Not Found with `{ "error": "Teacher not found" }` (idempotent per Principle X.2).
- **FR-010** (Stage 3 — API: DELETE class): The system MUST expose `DELETE /api/v1.0/classes/[ulid]` that performs a hard delete on the class. No referential-integrity check is required (no other table references `classes.id` outside the audit columns — per Principle X.2). On success, the route deletes the row and returns HTTP 200 OK with `{ "ulid": "<deleted-class-ulid>" }`. A second DELETE on the same `ulid` returns HTTP 404 Not Found with `{ "error": "Class not found" }` (idempotent per Principle X.2).
- **FR-011** (Stage 3 — auth + CSRF): Every `PUT` and `DELETE` request MUST be authenticated (Principle IV — session cookie; the auth middleware rejects with 401 when no valid session cookie is presented) and CSRF-protected (Principle IX.3 — the `X-CSRF-Token` header MUST match the `csrfToken` cookie via constant-time comparison; the CSRF middleware rejects with 403 when the pair does not match). The route handlers MUST NOT do their own session or CSRF lookup — the middleware owns that.
- **FR-012** (Stage 3 — content-type validation): Every `PUT` request MUST carry a `Content-Type: application/json` header; the route MUST reject with HTTP 415 Unsupported Media Type and `{ "error": "Content-Type must be application/json" }` otherwise (same rule that guards POST, per `003-backend-api-db/spec.md` FR-013). DELETE requests have no body and are not subject to the 415 check.
- **FR-013** (Stage 3 — Singapore contact-number rule): The Joi schema for the Teacher `contactNumber` field MUST validate against the regex `^[89]\d{7}$` — exactly 8 digits, must start with `8` or `9`. This is restored from the relaxed `^\d{8}$` pattern in `001-teachers/spec.md` Clarifications Session 2026-06-21 (see Clarifications Session 2026-06-22, contact-number rule restoration). The same rule applies on POST (Add Teacher) and PUT (Edit Teacher). The error message on rejection is `Contact number must start with 8 or 9 and be 8 digits.` The unit tests MUST cover the leading-digit rejection path (values starting with `0`–`7` and `10`–`99` are rejected).
- **FR-014** (Stage 3 — Joi schemas for PUT and DELETE): The Joi schemas for PUT mirror the POST shape (full-resource replacement, every mutable field required); the Joi schemas for DELETE are empty-body schemas that still run the validation step (per Principle VII — the route handler MUST run validation even when the body is empty).
- **FR-015** (Stage 3 — propagation contract): The Stage 3 PUT/DELETE endpoints, the form-teacher referential integrity rule, the restored Singapore contact-number rule, the `previousModifiedAt` extension on PUT 200 response bodies, and the deferred keyboard-accessibility scope decision are owned by this spec (`006-teachers-classes-mutations/spec.md`). The per-spec Clarifications amendments that propagate this spec's changes back into `001-teachers/spec.md` (FR-004 contact-number rule, FR-005a subject-active still applies on PUT, FR-005 email-unique still applies on PUT), `002-classes/spec.md` (FR-004 form-teacher-existence still applies on PUT, FR-005 form-teacher-uniqueness still applies on PUT, FR-005c name-uniqueness still applies on PUT, Edge Cases "teacher is deleted" superseded by Principle X.1), and `003-backend-api-db/spec.md` (FR-013 status-code table gains `200 OK` row, clarifies `404 Not Found` on DELETE, documents the optional `details` extension in the error envelope, and documents the `previousModifiedAt` field on PUT 200 responses as the spec'd extension to the standard response body) are flagged as Stage 3 follow-up TODOs and are the implementation step that follows `/speckit-plan`. **Stage 3 Out of Scope (expanded):** in addition to the constitution v2.5.0 Stage 3 Out of Scope list (bulk, soft delete, archive, PATCH, cascading delete, new entities, FK migration of audit columns), this spec explicitly defers **keyboard accessibility for the per-row `...` menu and the Delete confirmation modal** to a future-stage amendment (see Clarifications Q4); the mouse-only posture is intentional and is not a defect.
- **FR-016** (Stage 3 — concurrent-edit toast): When a successful UPDATE (PUT /api/v1.0/teachers/[ulid] or PUT /api/v1.0/classes/[ulid]) returns 200 OK with a `previousModifiedAt` field that differs from the `modifiedAt` value the client captured when the Edit form mounted, the UI MUST show a non-blocking antd warning notification reading `Note: this record was edited by another administrator at HH:MM:SS — your changes are saved, but please verify.` (where `HH:MM:SS` is the formatted value of `previousModifiedAt`). The notification is informational only — the update has already been persisted; the admin can dismiss it or act on it (e.g., re-open the record and verify nothing critical was lost). The notification MUST NOT block navigation, MUST NOT trigger a re-fetch, and MUST auto-dismiss after 8 seconds or when the admin closes it manually (whichever comes first). This preserves the constitution v2.5.0 strict-PUT last-write-wins semantics (no 409 on `version` mismatch; see the prior Clarifications Session 2026-06-22, Q4 in the `/speckit-specify` pass) while providing the opt-in concurrent-edit signal an admin needs to spot a clobber. The toast does NOT fire when the form is the only writer (i.e., when `previousModifiedAt === formLoadTime.modifiedAt`) — the comparison is the trigger, not the mere fact that `modified_at` was just updated.

### Key Entities

This spec does not introduce new entities — it operates on the existing Teachers and Classes entities from `001-teachers/spec.md` and `002-classes/spec.md`. The Stage 3 mutation endpoints reuse the same MySQL tables, typeORM entities, Joi schemas, and audit columns.

- **Teacher** (existing, from `001-teachers/spec.md`): a registered teacher. Stage 3 adds the UPDATE and DELETE mutations. All four mutable fields (`name`, `subject`, `email`, `contactNumber`) are submitted on PUT; the `ulid` is immutable and is the path parameter. The `subject` reference is resolved server-side from `subject.ulid` via `uq_subjects_ulid` (per FR-005a, 001-teachers). The Stage 3 contact-number rule (`^[89]\d{7}$`) applies on POST and PUT. The audit columns (`modified_at`, `modified_by`, `version`) are updated on every successful PUT; the row is removed on successful DELETE (the audit columns are NOT preserved on DELETE — Stage 3 is a hard delete; see Stage 3 Out of Scope).

- **Class** (existing, from `002-classes/spec.md`): a registered class with a form teacher. Stage 3 adds the UPDATE and DELETE mutations. The `formTeacher` reference is resolved server-side from `formTeacher.ulid` via `uq_teachers_ulid` (per FR-004, 002-classes). The form-teacher uniqueness invariant (FR-005, 002-classes) MUST be re-checked on PUT (a class updating to the same form teacher it already has is permitted; a class updating to a form teacher belonging to a different class is rejected with 409). DELETE on a class is unconstrained (no other table references `classes.id` outside the audit columns).

- **`details` extension on the error envelope** (NEW, owned by this spec): the standard `{ "error": "..." }` envelope from `003-backend-api-db/spec.md` is extended with an optional `details` field that carries structured information about the failure. The only Stage 3 use case is DELETE-Teacher (409), where `details` carries `{ "classUlid": "<classUlid>", "className": "<className>" }` (singular — the DB's `UNIQUE INDEX uq_classes_form_teacher_id` guarantees at most one affected class, so the prior array shape `classUlids[]` / `classNames[]` and the prior Q5 N > 5 truncation logic are superseded per Clarifications Session 2026-06-22 (DELETE-Teacher 409 envelope — one-to-one simplification)). The `error` field stays canonical and human-readable; `details` is a machine-readable extension that downstream consumers (UI notifications, automated tests, deep-links to `/classes/[ulid]/edit`) can use without parsing the error string. Other Stage 3 endpoints MAY use the `details` extension but are not required to.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An administrator can edit an existing teacher — navigate to `/teachers`, click the per-row `...` menu, click **Edit**, change any subset of `name`, `subject`, `email`, `contactNumber`, and submit — and see the updated row reflected in the Teachers list in under 30 seconds of total time, with no page reload beyond standard Next.js client-side navigation.
- **SC-002**: An administrator can delete an existing teacher — click the per-row `...` menu, click **Delete**, confirm the modal — and see the row disappear from the Teachers list in under 5 seconds, with the audit columns of any other rows unaffected.
- **SC-003**: 100% of DELETE-Teacher requests against a teacher who IS currently a form teacher of at least one class return HTTP 409 Conflict with the standard `{ "error": "Teacher is assigned as form teacher of class \"<className>\". Reassign or delete that class first.", "details": { "classUlid": "<classUlid>", "className": "<className>" } }` envelope (per FR-009, Clarifications Session 2026-06-22 (DELETE-Teacher 409 envelope — one-to-one simplification)), and the UI surfaces the single affected class name in a single antd error notification. Zero orphan `form_teacher_id` references exist on the `classes` table at any point in time (the referential integrity invariant holds across all concurrent operations).
- **SC-004**: 100% of second DELETE requests on the same `ulid` return HTTP 404 Not Found with the standard envelope, and the UI refreshes the list silently (no error notification on 404).
- **SC-005**: 100% of UPDATE-Teacher submissions with a `contactNumber` that does NOT match `^[89]\d{7}$` are rejected at the field level with HTTP 400 Bad Request and a field-level error reading `Contact number must start with 8 or 9 and be 8 digits.`, and the teacher is NOT updated.
- **SC-006**: 100% of UPDATE-Class submissions that change `formTeacher.ulid` to a teacher who is already the form teacher of a DIFFERENT class are rejected with HTTP 409 Conflict and a field-level error on the Form Teacher control; submissions that change `formTeacher.ulid` to the same form teacher the class already has are accepted with HTTP 200 OK (no `form_teacher_id` change → no uniqueness violation).
- **SC-007**: 100% of Stage 3 PUT and DELETE API calls (against `/api/v1.0/teachers/[ulid]` and `/api/v1.0/classes/[ulid]`) without a valid session cookie return HTTP 401 Unauthorized (auth middleware per Principle IV), and 100% without a matching `X-CSRF-Token` header return HTTP 403 Forbidden (CSRF middleware per Principle IX.3). Both rejections happen before the route handler runs.
- **SC-008**: 100% of API errors across the Stage 3 endpoints are returned with the agreed JSON error envelope (`{ "error": "..." }`, with the optional `details` extension on DELETE-Teacher 409) and the correct HTTP status code (`200` for successful UPDATE / first DELETE; `400` for Joi / payload validation; `401` for missing/invalid session; `403` for missing/invalid CSRF; `404` for second DELETE on a missing `ulid`; `409` for form-teacher referential integrity, duplicate email, duplicate class name, form-teacher collision on a different class; `415` for non-JSON content type on PUT; `500` for unhandled server failures; `503` for data-store unavailability).
