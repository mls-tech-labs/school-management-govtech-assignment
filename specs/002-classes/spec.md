## Clarifications

### Session 2026-06-18

- Q: Class `level` field — free-text or predefined list? → A: Predefined list (seeded, read-only in Stage 1). Mirrors the `subject` decision in `001-teachers`. The Add Class form exposes `level` as a dropdown populated from a seeded `levels` reference table (e.g., "Primary 1"…"Primary 6", "Secondary 1"…"Secondary 4"); Joi validates the submitted value against the closed set; adding new levels is deferred to a later stage (admin UI for the `levels` reference table) and is out of Stage 1 scope.
- Q: How should the admin pick the form teacher? → A: Searchable dropdown of existing teachers. The Add Class form's "Form Teacher" control is a dropdown (combo box) populated from the GET /api/v1.0/teachers response; the admin selects a teacher, and the form submits the selected teacher's `email` in the `teacherEmail` field — so the API contract is unchanged. The `404 "Teacher not found"` path is retained as a defence against the race where a teacher is deleted between page load and submit. When no teachers exist, the dropdown is empty and the Add Class form's submit button is disabled, with a clear "Add a teacher first" message. *Superseded by Clarifications, Session 2026-06-20 (POST/GET reference object shape): the form now submits the selected teacher's `ulid` nested under `formTeacher.ulid` (in a `{ ulid, name }` object), not the `email`/`teacherEmail` field; the nested `formTeacher.name` is a display hint and is ignored server-side. See FR-004, FR-005, FR-006, FR-007 below for the propagated wording.*
- Q: Should class-name uniqueness be a hard requirement? → A: Yes — class `name` is globally unique. Joi rejects empty / missing `name` with `400`; the MySQL `UNIQUE` constraint on `classes.name` makes the duplicate detection race-safe. On duplicate, the route returns `409 Conflict` with `{ "error": "Class name already in use" }`. This codifies the previous soft Assumption and aligns with the `409` pattern used for duplicate email (`001-teachers`) and "teacher already assigned" (`002-classes` FR-005).
- Q: Pagination for the Classes list? → A: No pagination in Stage 1. The GET endpoint returns the full list of classes in a single `{ "data": [...] }` response. The Stage 1 upper bound is ≤ 500 classes (see Assumptions); pagination is a future-stage amendment if the school outgrows that bound. This mirrors the `001-teachers` decision for API consistency.
- Q: What is the primary key of a `Class`? → A: Surrogate auto-increment `id`. The DB column is numeric and auto-generated; `name` carries a separate `UNIQUE` index (the one FR-005c adds). The `id` is **not** exposed in the Stage 1 API response (edit/delete are out of Stage 1 scope per the constitution), but the column exists so a future edit/delete endpoint can route by it without a schema migration.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Add a New Class with a Form Teacher (Priority: P1)

An administrator creates a new class by completing an "Add Class" form with the class's level (e.g., "Primary 1"), class name (e.g., "Class 1A"), and the email of an existing teacher who will serve as the class's form teacher, then submits the form. The system creates the class, links it to the chosen teacher, and confirms the new record was created.

**Why this priority**: A class cannot exist without a form teacher, and listing classes depends on the ability to create them. This is the foundational write path for the classes domain and the only way to exercise the teacher-as-form-teacher relationship that is central to the application's purpose.

**Independent Test**: Can be fully tested by submitting the Add Class form with a valid level, name, and the email of an existing teacher, then verifying that the class appears in the Classes list with the correct level, name, and form teacher name, and that a creation request returns a successful response with HTTP 201.

**Acceptance Scenarios**:

1. **Given** the administrator is on the Add Class screen in its empty/initial state, **When** the administrator enters a valid level, class name, and selects an existing teacher as the form teacher, and submits the form, **Then** the system records the class, associates the teacher as its form teacher, and the screen confirms the class was added.
2. **Given** the administrator is on the Add Class screen, **When** the administrator submits the form with one or more invalid or missing required fields (level, name, or form teacher), **Then** the screen shows the corresponding field-level error states and the class is not created.
3. **Given** no teacher is currently registered with the supplied `formTeacher.ulid`, **When** the administrator submits the Add Class form, **Then** the system rejects the submission with HTTP `404 Not Found` and shows a meaningful error indicating that the teacher could not be found.
4. **Given** the teacher identified by `formTeacher.ulid` is already the form teacher of another class, **When** the administrator submits the Add Class form for that same teacher, **Then** the system rejects the submission with HTTP `409 Conflict` and shows a meaningful error indicating that the teacher is already assigned as a form teacher.
5. **Given** a class with the same `name` already exists in the system, **When** the administrator submits the Add Class form with that name, **Then** the system rejects the submission with HTTP `409 Conflict` and shows a meaningful error indicating that the class name is already in use.

---

### User Story 2 - Retrieve the List of Classes (Priority: P1)

An administrator navigates to the Classes screen and sees the complete list of classes currently registered in the system, with each class showing its level, name, and the name of its form teacher.

**Why this priority**: The list view is the primary way the administrator confirms class creation succeeded and browses the existing classes. It is the read counterpart to Story 1 and surfaces the form-teacher relationship in a way the administrator can audit at a glance.

**Independent Test**: Can be fully tested by navigating to the Classes screen and verifying that all classes previously created are shown with their level, name, and form teacher name, or that an empty-state view is presented when no classes exist.

**Acceptance Scenarios**:

1. **Given** one or more classes are registered in the system, **When** the administrator opens the Classes screen, **Then** the screen lists every class with its level, name, and form teacher name, in a readable filled state.
2. **Given** no classes are registered, **When** the administrator opens the Classes screen, **Then** the screen shows the empty state with a clear prompt indicating that no classes exist and an entry point to add one.
3. **Given** the Classes screen is loading data, **When** the request to retrieve classes fails, **Then** the screen shows a meaningful error message and does not display stale or partial data.

---

### Edge Cases

- What happens when the Add Class form is submitted with a `level` that is not in the predefined list (unknown, removed, or marked inactive)? — The form must show a field-level Level error and reject submission with HTTP `400`. On the wire, the lookup is by `level.ulid` (per `003-backend-api-db/spec.md` Clarifications, Session 2026-06-20 (POST/GET reference object shape)); an unknown or inactive `level.ulid` triggers the 400.
- What happens when the admin opens the Add Class screen with no teachers registered? — The Form Teacher dropdown is empty, the form's submit button is disabled, and a clear "Add a teacher first" message links the admin to the Add Teacher flow.
- What happens when the Add Class form is submitted with a `name` that matches an existing class? — The form must show a field-level Name error and reject submission with HTTP `409` and `{ "error": "Class name already in use" }`. Two simultaneous submissions with the same name cannot both succeed (race-safe via the `UNIQUE` constraint).
- What happens when the administrator submits the Add Class form with a `formTeacher.ulid` that does not match any registered teacher? — The system must treat this as a "teacher not found" condition (HTTP `404`) and reject submission with `{ "error": "Teacher not found" }`. On the wire, the lookup is by `formTeacher.ulid` (per `003-backend-api-db/spec.md` Clarifications, Session 2026-06-20 (POST/GET reference object shape)).
- What happens when the request body carries a `level` or `formTeacher` object whose nested `name` field does not match the row identified by its `ulid` (e.g., `{ ulid: "01H...", name: "Wrong Label" }`)? — The server ignores `name`; only `ulid` is consulted for the lookup. The response echoes the authoritative `name` from the referenced row, not the client-supplied value.
- What happens when two administrators submit the Add Class form for the same teacher at the same time? — The system must accept at most one of the submissions and reject the other with the "teacher already assigned" error, so the uniqueness invariant on form teacher is preserved. Uniqueness is by `classes.form_teacher_id` (resolved from `formTeacher.ulid` per FR-004).
- What happens when a teacher is deleted (or otherwise no longer available) after a class was created with that teacher as the form teacher? — This scenario is out of scope for v1; the class keeps the form teacher reference as it was at creation time.
- What happens when the network is unavailable while submitting the Add Class form? — The screen must show a meaningful error and the form's input is preserved so the administrator can retry.
- What happens when the administrator reloads the Classes screen mid-load? — The screen must show a consistent loading or error state and must not show mixed or stale data.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST provide a screen titled "Add Class" that exposes input controls for **Level** (a dropdown populated from the predefined, seeded `levels` reference list — see Clarifications, Session 2026-06-18), **Name**, and **Form Teacher** (a searchable dropdown of currently registered teachers, populated from the existing-teachers list — see Clarifications, Session 2026-06-18), with the labels, order, and field types matching the Figma design (`./designs/classes/Add Class - Empty State.png` and `./designs/classes/Fields.png`).
- **FR-002**: The system MUST require Level, Name, and Teacher Email to be supplied and valid before the Add Class form can be submitted successfully. *(Superseded by Session 2026-06-20 (POST/GET reference object shape): "Teacher Email" is now `formTeacher.ulid` — a 26-character Crockford Base32 ULID nested inside `formTeacher: { ulid, name }`. The nested `formTeacher.name` is optional and is not validated. See FR-004, FR-005, FR-005b, FR-006, FR-007.)*
- **FR-003**: The system MUST validate that the Teacher Email field contains a syntactically valid email address. *(Superseded by Session 2026-06-20 (POST/GET reference object shape): the wire format is now `formTeacher: { ulid, name? }`, not a flat email string. Validation matches `ulid` against the `uq_teachers_ulid` index; the `teacherEmail` field is no longer accepted.)*
- **FR-004**: The system MUST treat the Form Teacher's `ulid` as a reference to an existing teacher registered in the system (see the Teachers feature); the system MUST reject the submission with a meaningful error if no teacher with that `ulid` exists. On the wire, Form Teacher is a nested object `{ ulid: string, name?: string }` (per `003-backend-api-db/spec.md` Clarifications, Session 2026-06-20 (POST/GET reference object shape)): the route handler resolves `formTeacher.ulid` to `teachers.id` via `uq_teachers_ulid` before insert; the nested `formTeacher.name` is a display hint and is NOT validated against the row identified by `ulid`.
- **FR-005**: The system MUST enforce the invariant that a teacher can be the form teacher of **at most one** class. Submitting a class whose `formTeacher.ulid` is already the form teacher of another class MUST be rejected with a meaningful error. Uniqueness is enforced by the `UNIQUE` constraint on `classes.form_teacher_id` (per `003-backend-api-db/spec.md` FR-008).
- **FR-005a**: The system MUST require the selected **Level** to reference an **active** entry in the predefined `levels` reference list. On the wire, Level is a nested object `{ ulid: string, name?: string }` (per `003-backend-api-db/spec.md` Clarifications, Session 2026-06-20 (POST/GET reference object shape)): the route handler resolves `level.ulid` to `levels.id` via `uq_levels_ulid` before insert; the nested `level.name` is a display hint and is NOT validated against the row identified by `ulid`. Submissions whose `level.ulid` is missing, unknown, or marked inactive MUST be rejected with a field-level error on the Level control.
- **FR-005b**: When no teachers are currently registered, the Add Class screen MUST present the Form Teacher dropdown in an empty state with a clear "Add a teacher first" message, and the form's submit button MUST be disabled. Submitting a class with a `formTeacher.ulid` that does not reference any registered teacher MUST be rejected with HTTP `404` and `{ "error": "Teacher not found" }` (covers the race where a teacher is deleted between page load and submit — see Clarifications, Session 2026-06-18).
- **FR-005c**: The system MUST enforce global uniqueness on the class `name`. Submitting a class whose `name` matches an existing class MUST be rejected with HTTP `409 Conflict` and `{ "error": "Class name already in use" }`. Uniqueness is enforced by the MySQL `UNIQUE` constraint on `classes.name` so the behaviour is race-safe by construction (see Clarifications, Session 2026-06-18).
- **FR-006**: The system MUST expose a public API endpoint to create a class at `POST /api/v1.0/classes` (per FR-022, owned by `003-backend-api-db`) that accepts `level` and `formTeacher` as nested `{ ulid, name }` objects (per `003-backend-api-db/spec.md` Clarifications, Session 2026-06-20 (POST/GET reference object shape)) along with `name` in the request body, and, on success, returns a confirmation response with HTTP status 201. The 201 response body MUST include the newly-created class's `ulid` (per FR-014) so the client can store the sync handle without a separate GET. The 201 body MUST echo `level` and `formTeacher` as nested `{ ulid, name }` objects on the same shape as the request (round-trip consistency). The Add Class UI's Form Teacher dropdown is unchanged in behaviour — still a searchable dropdown of existing teachers — but the value it submits is the selected teacher's `ulid` (nested under `formTeacher.ulid`) rather than the selected teacher's `email` (see Clarifications, Session 2026-06-18 and Session 2026-06-20).
- **FR-007**: The system MUST expose a public API endpoint at `GET /api/v1.0/classes` (per FR-022, owned by `003-backend-api-db`) to list all classes that, on success, returns the full list of classes wrapped in a `data` array with HTTP status 200, with each entry containing `ulid` (per FR-014), `name`, `level` (nested `{ ulid, name }` per FR-005a and `003-backend-api-db/spec.md` Clarifications, Session 2026-06-20 (POST/GET reference object shape)), and `formTeacher` (nested `{ ulid, name }` per FR-004). Stage 1 does not paginate; the response is the complete set (see Clarifications, Session 2026-06-18).
- **FR-008**: The system MUST provide a screen titled "Classes" that lists the registered classes with each entry showing `level.name` (resolved from the nested `{ ulid, name }` object on each entry), `name`, and `formTeacher.name` (resolved from the nested `{ ulid, name }` object on each entry), in a layout consistent with the Figma design (`./designs/classes/Classes - Empty State.png` and `./designs/classes/Classes - Filled State.png`).
- **FR-009**: The Classes screen MUST present an empty state when no classes are registered, and a filled state when at least one class exists, both matching the corresponding Figma design.
- **FR-010**: All API endpoints for this feature MUST, on any error condition, return a JSON response body of the form `{ "error": "Some meaningful error message" }` together with an appropriate HTTP status code. The status-code mapping MUST be: `400 Bad Request` for Joi / payload validation failures (missing/invalid `level.ulid`, `name`, or `formTeacher.ulid`; unknown/inactive `level.ulid`); `401 Unauthorized` for protected endpoints accessed without a valid session cookie (inherited from `specs/003-backend-api-db/spec.md` FR-013; the auth middleware is owned by `specs/004-user-auth/spec.md` and rejects the request before the handler runs); `404 Not Found` for a non-existent teacher (`formTeacher.ulid` does not match any registered teacher); `409 Conflict` for "teacher already assigned" to another class **or** duplicate class `name`; `415 Unsupported Media Type` for requests whose `Content-Type` is not `application/json`; `500 Internal Server Error` for unhandled server failures; `503 Service Unavailable` when the data store is briefly unreachable.
- **FR-011**: The Add Class screen MUST preserve the administrator's input on a failed submission and surface the field-level errors shown in the Figma error state.
- **FR-012**: Class data and the form-teacher relationship MUST be persisted so that they survive server restarts and remain consistent with the Teachers feature (i.e., a class's form teacher is always an existing teacher).
- **FR-013** (inherited from `003-backend-api-db/spec.md` FR-018 / FR-019 / FR-020 — audit columns): Both the `classes` and `levels` tables MUST carry the six-column audit pattern (`id`, `created_at`, `created_by`, `modified_at`, `modified_by`, `version`). `id` is the surrogate primary key on both tables; `classes.name` and `levels.name` are preserved as `UNIQUE NOT NULL`; the foreign key columns in `classes` are renamed `level_id` and `form_teacher_id`, referencing `levels.id` and `teachers.id` respectively. The Stage 1 public API responses continue to expose natural-key field names (`classes.level`, `classes.name`, `classes.formTeacher.name`, `levels.name`, `levels.active`) — none of the audit columns are exposed in the response body.
- **FR-014** (inherited from `003-backend-api-db/spec.md` FR-021 — ULID column): Both the `classes` and `levels` tables MUST carry the `ulid CHAR(26) NOT NULL UNIQUE` column (per `003-backend-api-db/spec.md` FR-021). `ulid` is generated server-side via the `ulid` npm package (route handler or typeORM `@BeforeInsert()` hook), carries a `UNIQUE` index per table, is **exposed** in every Stage 1 GET and POST response as the frontend-stable sync handle (the deliberate exception to the FR-020 "audit columns hidden" rule), and is **not** a foreign-key target — joins remain on the surrogate `id` (per FR-019). The Stage 1 public API responses gain a top-level `ulid` field on each class and each level; the natural-key fields (`classes.level`, `classes.name`, `classes.formTeacher.name`, `levels.name`, `levels.active`) are unchanged.

### Key Entities

- **Class**: Represents a class registered in the system.
  - `id` (numeric, auto-generated, primary key) — the surrogate identifier of the class. **Not** exposed in the Stage 1 API response (see Clarifications, Session 2026-06-18); exists so a future edit/delete endpoint can route by it without a migration.
  - `level_id` (foreign key → `levels.id`, required; the route handler resolves the request body's `level.ulid` (per FR-005a and `003-backend-api-db/spec.md` Clarifications, Session 2026-06-20 (POST/GET reference object shape)) to `levels.id` via `uq_levels_ulid` before insert; the public API exposes the reference as a nested `{ ulid, name }` object on both POST and GET) — the educational level of the class, chosen from the predefined `levels` reference list (see Level entity below). Examples: "Primary 1", "Primary 2", …, "Secondary 4".
  - `name` (string, required, `UNIQUE NOT NULL`) — the class's display name (e.g., "Class 1A"); the format is determined by the Figma design. Uniqueness is enforced by a separate `UNIQUE` index (see `FR-005c`); the natural-key status is preserved even though `id` is the surrogate PK (per FR-018).
  - `form_teacher_id` (foreign key → `teachers.id`, required, `UNIQUE`; the route handler resolves the request body's `formTeacher.ulid` (per FR-004 and `003-backend-api-db/spec.md` Clarifications, Session 2026-06-20 (POST/GET reference object shape)) to `teachers.id` via `uq_teachers_ulid` before insert; the public API exposes the reference as a nested `{ ulid, name }` object on both POST and GET) — the teacher who serves as the form teacher of the class.
    - The Add Class UI is still a searchable dropdown of existing teachers (per Clarifications, Session 2026-06-18, Q2); the dropdown submits the selected teacher's `ulid` (nested under `formTeacher.ulid`) rather than the selected teacher's `email`.
    - The FK on `form_teacher_id` enforces referential integrity (per FR-019).
  - `ulid` (string, required, `UNIQUE`) — the frontend-stable sync handle (per FR-014 / `003-backend-api-db/spec.md` FR-021); exposed in the Stage 1 `GET /api/v1.0/classes` and `POST /api/v1.0/classes` responses as a top-level field on each record.
  - Inherits the six audit columns from FR-018: `created_at`, `created_by`, `modified_at`, `modified_by`, `version` (plus the surrogate `id` PK already listed above).
  - Relationships: a Class references exactly one Teacher via the form-teacher relationship. A Teacher may be the form teacher of zero or one Class (see FR-005).

- **Level** (reference table, seeded in Stage 1; admin-managed in a later stage):
  - `id` (surrogate PK, per FR-018) — internal identifier; not exposed in the Stage 1 API response.
  - `name` (string, required, `UNIQUE NOT NULL`) — display name of the level as it appears in the Add Class dropdown (e.g., "Primary 1", "Primary 2", …, "Secondary 4"). The natural-key identifier; preserved as `UNIQUE NOT NULL` (previously the PK).
  - `active` (boolean, default `true`) — whether the level is currently selectable in the Add Class form. Stage 1 treats this list as read-only and seeds it; admin authoring of levels is out of Stage 1 scope (see Assumptions).
  - `ulid` (string, required, `UNIQUE`) — the frontend-stable sync handle (per FR-014 / `003-backend-api-db/spec.md` FR-021); exposed in the `GET /api/v1.0/levels` response as a top-level field on each record.
  - Inherits the six audit columns from FR-018: `id` (surrogate PK), `created_at`, `created_by`, `modified_at`, `modified_by`, `version`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An administrator can create a new class and see the class appear in the Classes list in under 30 seconds of form time, with no page reload required beyond standard navigation.
- **SC-002**: 100% of successful Add Class submissions result in a class record that is persisted and visible on the Classes screen after a full page refresh, with the correct form teacher name displayed.
- **SC-003**: 100% of Add Class submissions with an unknown `formTeacher.ulid`, a `formTeacher.ulid` already assigned to another class as form teacher, an unknown `level.ulid`, or a duplicate class `name` are rejected with a field-level or form-level error message.
- **SC-004**: The invariant "a teacher can be the form teacher of at most one class" holds for 100% of class records in the system at all times, including under concurrent submissions.
- **SC-005**: The Classes screen presents the empty state on first load (zero classes) and the filled state immediately after the first successful creation, with no stale or empty data shown.
- **SC-006**: 100% of API errors (validation, not-found, conflict, content-type, server, data store) for the classes endpoints are returned with the agreed JSON error envelope (`{ "error": "..." }`) and the correct HTTP status code (`400` for validation, `404` for teacher not found, `409` for duplicate name or teacher already assigned, `415` for non-JSON content type, `500` for unhandled server failures, `503` when the data store is briefly unreachable), so they can be consumed by automated test tools.
- **SC-007**: 100% of GET and POST API responses for classes expose the `level` and `formTeacher` fields as nested `{ ulid: string, name: string }` objects on every entry. The `ulid` values match the `ulid` columns of the referenced rows in `levels` and `teachers`. The POST request body uses the same nested shape with `ulid` required (26-character Crockford Base32) and `name` optional; the server uses `ulid` for the lookup (against `uq_levels_ulid` / `uq_teachers_ulid`) and ignores `name` (per `003-backend-api-db/spec.md` Clarifications, Session 2026-06-20 (POST/GET reference object shape)).

## Assumptions

- The administrator accesses the application on a modern desktop browser; mobile/responsive support is not required for the Classes feature in v1.
- The Teachers feature (see `specs/001-teachers/spec.md`) is in place before this feature is implemented; the Add Class form's `formTeacher.ulid` field is validated against the existing teacher records (looked up via `uq_teachers_ulid` per FR-004). If the Teachers feature is not yet present, an equivalent minimal teacher record set (e.g., a fixture) is required for testing.
- The Add Class form's field types (e.g., text input, dropdown, validation rules) follow the Figma designs in `./designs/classes/`. The "Fields" design asset is treated as the authoritative reference for field types and validation cues.
- The list of allowed `level` values is provided by a seeded `levels` reference table (e.g., "Primary 1"…"Primary 6", "Secondary 1"…"Secondary 4"). The table is read-only in Stage 1; admin authoring of levels is a future-stage amendment. The list is closed and any submitted level not in the table is rejected with a field-level error (see Clarifications, Session 2026-06-18). On the wire, the lookup is by `level.ulid` (per `003-backend-api-db/spec.md` Clarifications, Session 2026-06-20 (POST/GET reference object shape)).
- The Form Teacher control on the Add Class form is a searchable dropdown of existing teachers, populated from `GET /api/v1.0/teachers`. The wire shape submitted to the API is now `{ "formTeacher": { "ulid": "...", "name": "..." } }` (per `003-backend-api-db/spec.md` Clarifications, Session 2026-06-20 (POST/GET reference object shape)); the dropdown is still a UX choice, but the value it submits is the selected teacher's `ulid` (nested under `formTeacher.ulid`) rather than the selected teacher's `email`. The `404 "Teacher not found"` path is retained as a race-condition defence, not a normal user error.
- The `name` of a class is unique within the system; this is now codified as `FR-005c` (was previously a soft Assumption). The MySQL `UNIQUE` constraint on `classes.name` enforces it race-safely.
- Stage 1 assumes a realistic upper bound of **≤ 500 classes** for the system. The GET endpoint returns the full list in a single response (no pagination); if the school outgrows this bound, pagination is added in a future stage as an amendment to FR-007 (see Clarifications, Session 2026-06-18). This matches the `001-teachers` decision.
- The `Class` table has a numeric, auto-generated `id` primary key (surrogate). The `id` is **not** included in the Stage 1 API response — the wire shape remains `{ "ulid", "level", "name", "formTeacher": { "name" } }` for each entry in `GET /api/v1.0/classes` and the POST response is a confirmation. The column exists so a future edit/delete endpoint can route by id without a schema migration (see Clarifications, Session 2026-06-18).
- The cross-cutting status-code table for this spec includes `400` (validation) / `404` (teacher not found) / `409` (duplicate name or teacher already assigned) / `415` (request `Content-Type` is not `application/json`) / `500` (unhandled server failure) / `503` (data store briefly unreachable). Aligns with `003-backend-api-db/spec.md` Clarifications, Session 2026-06-18.
- The Classes feature does not edit or delete classes in v1; create and list are the only two operations. Edit/delete are out of scope until a future feature amends this spec.
- role-based access control are explicitly out of scope per the requirements ("you do not need to implement login and access control").
