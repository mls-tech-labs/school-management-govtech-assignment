# Research: User Authentication (004-user-auth)

**Date**: 2026-06-21
**Spec**: [./spec.md](./spec.md)
**Plan**: [./plan.md](./plan.md)

This document is the Phase 0 research output for the auth feature.
It resolves every `[NEEDS CLARIFICATION]` left open in `spec.md`
(see Clarifications — Q1..Q6 + Q1 round 1) and records the
implementation choices, the alternatives that were rejected, and
the rationale. The decisions here are referenced by `plan.md`,
`data-model.md`, `contracts/auth.yaml`, and `quickstart.md`.

The decisions are grouped by the **question they resolve**, not
by file. Each entry is **Decision · Rationale · Alternatives
considered**, in that order, so the spec-level question and the
implementation-level answer are traceable in one read.

## 1. Password hashing algorithm (resolves spec Clarifications Q4 + Assumption block)

**Decision**: **argon2id** via the `argon2` npm package, configured
with the package's `argon2id` default parameters
(`memoryCost = 65536 KiB`, `timeCost = 3`, `parallelism = 4`). Both
hash and salt are stored in the `users` row as separate
`VARCHAR(255)` columns; the salt is generated by the helper itself
(`argon2`'s hash output already embeds the salt in its
`$argon2id$...` envelope, so the row's `salt` column stores the
matching cleartext salt separately for compatibility with the
`npm run seed:admin` SQL-printing path that needs a discrete salt
column).

**Rationale**: argon2id is the **OWASP Password Storage Cheat Sheet
(2024) primary recommendation** for new applications. It is
memory-hard (resistant to GPU and ASIC attacks), has first-class
TypeScript bindings, and is a single-dependency add. The cost
parameters are tuned so that a single hash takes ~50 ms on the
target server hardware — slow enough to deter brute-force, fast
enough that the login endpoint's p99 stays under the budget. The
separate `salt` column is a deliberate contract decision (not a
copy of the `argon2`-embedded salt) so the `seed:admin` helper can
emit SQL with a salt that is verifiable out-of-band.

**Alternatives considered**:

- **bcrypt** (`bcrypt` npm package) — mature, widely deployed, but
  GPU-bound; the OWASP recommendation has moved off bcrypt as the
  primary choice in 2024+. Rejected for greenfield use.
- **scrypt** (`crypto.scrypt` from Node stdlib) — memory-hard, zero
  new deps, but the parameter set is awkward to expose at the
  helper level (the JS API uses a `Keylen` + `cost` / `blockSize` /
  `parallelization` set with different semantics from the
  `argon2id` envelope). Rejected — the `seed:admin` helper would
  need to mirror the same parameter set verbatim, which is a known
  source of cross-implementation drift.
- **PBKDF2** (`crypto.pbkdf2Sync` from Node stdlib) — weakest of
  the four; not memory-hard. Rejected.

## 2. Redis client choice

**Decision**: **`ioredis`** (npm). Full TypeScript types ship with
the package, no `@types/*` needed. Single client instance, created
in `lib/db/redis.ts`, exported as a singleton `redis` and consumed
by `lib/auth/session.ts`.

**Rationale**: `ioredis` is the most widely-deployed Redis client
in the Next.js + Node ecosystem. It supports the standalone /
sentinel / cluster topologies behind a single client interface
(forward-compat if a future stage needs HA Redis), it has a
sensible offline-friendly error model (the `maxRetriesPerRequest`
default behaviour raises on connection failure, which is what the
auth middleware needs to translate to `503`), and its TypeScript
ergonomics are well-validated against `strict: true`.

**Alternatives considered**:

- **`redis` (node-redis v4+)** — official, ESM-first, modern API,
  but the `strict: true` typings on a Next.js Route Handler have
  historically needed a small `@ts-ignore` for the command result
  inference in some versions. Rejected for typing friction.
- **`@upstash/redis`** — HTTP-based, works in edge runtimes.
  Rejected because the auth middleware runs in the Node runtime
  (not edge), so the HTTP indirection is unnecessary.

## 3. Session token generation (resolves spec FR-016)

**Decision**: `crypto.randomBytes(32).toString('base64url')` from
Node's standard library — 32 bytes of CSPRNG output (256 bits of
entropy), encoded as URL-safe base64 without padding (43
characters). The token is stored as the Redis key exactly as
emitted, and is set on the response cookie in the same form.

**Rationale**: The spec's `Recommended default` was
`crypto.randomUUID()`. UUID v4 carries only ~122 bits of entropy
(128 minus the 4 version bits and 2 variant bits) — at the
recommended-default end of FR-016's "at least 128 bits" range. A
256-bit token from `crypto.randomBytes` is on the **safe** side of
that floor at no measurable cost, and `base64url` encoding is the
canonical cookie-safe representation (RFC 4648 §5). This shifts
the decision from "the minimum the spec allowed" to "the safe
side of the minimum", which is the right default for a session
secret.

**Alternatives considered**:

- **`crypto.randomUUID()`** — the spec's named recommendation;
  works, but the entropy budget is the spec's floor, not a
  safety margin. Documented above.
- **`uuid` npm package v7** — sortable, but adds a dep for no
  functional gain over `crypto.randomBytes`. Rejected.

## 4. Session cookie attributes (resolves spec Q5 + FR-017 / FR-018)

**Decision**: cookie name = `pvt_edu_session`. Attributes:

| Attribute | Value | Source |
|---|---|---|
| `Name` | `pvt_edu_session` | this research item |
| `Value` | `crypto.randomBytes(32).toString('base64url')` | research §3 |
| `Path` | `/` | spec FR-017 |
| `Domain` | not set (host-only) | this research item |
| `Max-Age` | `1800` (= `SESSION_TTL_SECONDS`) | spec FR-015 |
| `Expires` | not set (Max-Age is enough) | RFC 6265 §4.1.2.2 |
| `HttpOnly` | `true` | spec FR-017 |
| `Secure` | env-driven: `SESSION_COOKIE_SECURE` (default `NODE_ENV === 'production'`) | spec FR-017 (HTTPS-only in prod, relaxed in dev per Principle IV) |
| `SameSite` | `Strict` | spec FR-017 |
| `Priority` | not set | n/a |

**Rationale**: `pvt_edu_session` is prefixed to avoid collision
with any framework-set cookie (`connect.sid`, `next-auth.*`,
etc.). Host-only (`Domain` unset) is the correct default for a
single-host deployment and matches the spec's "the cookie Domain
is the application's host (cross-host scoping is out of scope for
Stage 2)" wording. `Secure` is driven by the env var so the
local-dev HTTP case is honest (no surprise cookie drops) and the
production HTTPS case is correct by default.

**Logout cookie** (spec FR-018) sets the same `Name`, `Path`,
`HttpOnly`, `Secure`, and `SameSite` attributes with
`Value = ""`, `Max-Age = 0`, and `Expires = <RFC-1123 past date>`
per RFC 6265 §4.1.1.

## 5. Local-dev HTTP posture for the `Secure` cookie flag (resolves spec Assumption block)

**Decision**: env var `SESSION_COOKIE_SECURE` (string `"true"` or
`"false"`), defaulting to `NODE_ENV === 'production'`. Read in
`lib/auth/cookie.ts` at module load; the middleware and the login
handler both consume the resulting boolean.

**Rationale**: Two competing concerns meet here:

1. **Production safety** — the `Secure` flag MUST be on for any
   HTTPS deployment; a missing flag in prod is a session-hijack
   vulnerability.
2. **Local-dev usability** — the local dev server runs over HTTP
   (`http://localhost:3000`); a hard-coded `Secure` flag would
   drop the cookie on every response and make login impossible.

An env var with a `NODE_ENV`-derived default is the **fail-closed
default** (production = secure) that lets the user flip the switch
without code changes for dev. Documented in `.env.example`.

**Alternatives considered**:

- **Hard-coded `Secure = NODE_ENV === 'production'`** — works,
  but couples the cookie flag to the Node runtime concept of
  `NODE_ENV`, which is not always set correctly in containerised
  deployments (e.g., a staging container behind HTTPS might run
  with `NODE_ENV=staging` and drop the cookie). Rejected.
- **Always-on `Secure`** — fails in dev. Rejected.
- **Always-off `Secure`** — fails in prod. Rejected.

## 6. `POST /api/v1.0/login` redirect-target preservation (resolves spec FR-004 + FR-021)

**Decision**: A two-step URL preservation pattern.

1. **On the React route guard** (`lib/auth/RouteGuard.tsx`,
   mounted at the layout for any private page): when
   `GET /api/v1.0/me` returns `401`, the guard reads
   `window.location.pathname + window.location.search`, encodes
   it with `encodeURIComponent`, and navigates the browser to
   `/login?redirectTo=<encoded>`. The encoded value is validated
   to start with a single `/` (rejects `//evil.example.com` and
   absolute URLs).
2. **On the login page** (`app/login/page.tsx`): on successful
   login (`POST /api/v1.0/login` → `200 OK`), the page reads
   `redirectTo` from the query string, validates it again with
   the same "starts with single `/`" rule, and navigates to it;
   if missing or invalid, the page navigates to
   `LOGIN_REDIRECT_DEFAULT` (env var, default `/`).

**Rationale**: Two independent validation steps (route guard + login
page) prevent an open-redirect vulnerability from a crafted
`redirectTo` query param. The single-slash prefix check is the
canonical "same-origin only" guard from OWASP. The
`LOGIN_REDIRECT_DEFAULT` env var lets the deployment point the
fallback somewhere other than `/` (e.g., `/dashboard`) without a
code change.

**Logout** (spec Clarifications Q5 round 1): always navigate to
`/login` with **no** `redirectTo` param — the post-logout landing
is the same as the fresh-visit landing.

**Alternatives considered**:

- **`sessionStorage`** — works, but the route guard runs on every
  mount, not every navigation; if the guard catches a `401` and
  writes to `sessionStorage`, a later navigation to the same
  private page (e.g., from a bookmark) would re-read the value
  and re-redirect. The query-string approach is navigation-time
  and self-clearing. Rejected.
- **`history.replaceState` + `document.referrer`** — too clever,
  too easy to get wrong, no security benefit over the query
  string. Rejected.

## 7. React route guard pattern (resolves spec FR-019..FR-022)

**Decision**: a client component, `lib/auth/RouteGuard.tsx`,
exported as `RouteGuard` (function component). It is mounted in
the layout that wraps every private page (e.g.,
`app/(private)/layout.tsx`). On mount it calls
`GET /api/v1.0/me` via the existing `lib/api/response.ts`
helpers; on `200` it renders `children`; on `401` it pushes the
`/login?redirectTo=<encoded current URL>` redirect per research
§6.

**Rationale**: The spec says "calls `GET /api/v1.0/me` on mount" —
that is client-component mount behaviour, not a Next.js
`middleware.ts` (which runs in the edge runtime and cannot reach
the application's Redis client). A client hook is the lowest
ceremony approach: it works with the existing App Router layout
system, the existing `lib/api/*` helpers, and the existing
`antd` + Tailwind primitives (Principle VIII). It also matches
the `SC-008` / `SC-009` acceptance scenarios (URL navigation
triggers the guard; valid cookie → page renders; invalid cookie
→ `/login`).

**Alternatives considered**:

- **`middleware.ts`** — runs in edge runtime; would need a separate
  HTTP client to call the application's own `GET /api/v1.0/me`
  (because the middleware can't share state with the Node
  runtime's Redis client). Adds an internal HTTP round-trip per
  navigation. Rejected.
- **Server component that calls `GET /api/v1.0/me`** — works, but
  the response of the server component is the initial page
  payload; the route-guard-driven client redirect for the
  `401` case becomes a server-side 307 / 308 redirect, which
  means the URL bar already shows `/login?redirectTo=...` on the
  first paint. Functionally correct, but harder to test and
  harder to share the redirect URL with the login page. Rejected.

## 8. `npm run seed:admin` helper (resolves spec FR-026)

**Decision**: TypeScript script at `scripts/seed-admin.ts`, run via
`tsx` (a devDependency already used by the test pipeline).

```text
$ npm run seed:admin -- --confirm --username=admin --password=<plaintext>
```

Behaviour (per spec FR-026):
- Refuses to run without `--confirm`.
- Loads `lib/auth/password.ts` and calls `hashPassword(plaintext)`
  to obtain `{ hash, salt }`.
- Generates a fresh `ulid` via `lib/ulid.ts`.
- Prints a parameterised `INSERT INTO users (...)` statement to
  stdout (one row, all columns, the `password` and `salt` columns
  populated from the helper output).
- Does **not** touch the database — it is a hash-and-print helper
  only (per spec FR-026). The user pipes the printed SQL into
  `mysql` against the user-prepared MySQL container.

**Rationale**: Keeping the hash + salt generation in the same
helper the application uses (`lib/auth/password.ts`) eliminates
algorithm/parameter drift between the seed path and the verify
path — a known root cause of "seed worked but login fails" bugs.
The `tsx` runner is already a devDependency for the test suite,
so no new tooling is needed. The `--confirm` flag is required to
prevent unattended shell pipelines from silently printing SQL.

**Alternatives considered**:

- **A standalone `bcrypt`-flavoured shell script** — would
  introduce a parallel password-hashing implementation. Rejected
  by the same drift argument above.
- **A `npm run seed:admin` that connects to MySQL and `INSERT`s
  directly** — violates spec FR-026 ("MUST NOT touch the
  database directly"). Rejected.

## 9. `.env` keys added by this feature (resolves spec Assumption block + `.env` discipline)

**Decision**: the following keys are added to `.env.example` (and
to the application's runtime config loader). All keys are
**fail-closed** on missing-required (per the project's `.env`
discipline: ship defaults in `.env.example`; required keys
missing at runtime cause a fail-fast startup error, not a silent
default).

| Key | Type | Default | Required? | Purpose |
|---|---|---|---|---|
| `REDIS_URL` | string | — | **Yes** | Redis connection string (e.g., `redis://localhost:6379`). Missing → fail-fast at boot. |
| `SESSION_COOKIE_NAME` | string | `pvt_edu_session` | No | Cookie name (research §4). |
| `SESSION_COOKIE_SECURE` | `true` \| `false` | `NODE_ENV === 'production'` | No | `Secure` flag (research §5). |
| `SESSION_TTL_SECONDS` | integer string | `1800` | No | Hard 30-minute TTL (spec FR-015). |
| `LOGIN_REDIRECT_DEFAULT` | path string | `/` | No | Post-login fallback path (research §6). |
| `PASSWORD_HASH_ALGO` | string | `argon2id` | No | Hash algorithm name; one allowed value for now. Pinned so a future swap is a single-line edit. |

**Rationale**: minimal-but-necessary per the project's
`.env`-driven config discipline (per the constitution's
**Configuration** clause under Technical Stack Constraints). The
two required keys (`REDIS_URL` — and `MYSQL_URL` already required
by Stage 1) are the smallest set that allows the auth feature to
boot; every other key has a safe default that matches the spec.

**Alternatives considered**:

- **Reading `REDIS_URL` from `process.env.REDIS_URL` with no
  default + a `throw new Error(...)` if missing** — the chosen
  pattern, but centralised in `lib/config.ts` so the missing-key
  error message is uniform across all features. Documented
  inline.
- **Hard-coded default for `REDIS_URL` (e.g., `redis://localhost:6379`)** — would mask configuration mistakes; the user
  would never learn they needed to set it. Rejected per the
  fail-closed principle.

## 10. Auth middleware module layout (resolves spec FR-010..FR-013 + Constitution → Principle VI)

**Decision**: pure-function modules under `lib/auth/`:

| File | Exports | Style |
|---|---|---|
| `lib/auth/password.ts` | `hashPassword(plain)`, `verifyPassword(plain, hash, salt)` | pure function, calls `argon2` internally; no I/O beyond the hash op |
| `lib/auth/session.ts` | `createSession(user)`, `getSession(sessionId)`, `destroySession(sessionId)`, `Session` type | pure function on top of the `redis` singleton; returns `null` on miss |
| `lib/auth/cookie.ts` | `sessionCookieName`, `setSessionCookie(res, sessionId)`, `clearSessionCookie(res)`, `readSessionCookie(req)` | pure function; reads `SESSION_COOKIE_*` env at module load |
| `lib/auth/middleware.ts` | `withAuth(handler)`, `PUBLIC_PATHS` constant (the exempt list from spec FR-011) | wraps a Next.js Route Handler; returns the same shape |
| `lib/auth/log.ts` | `logAuthLogin(outcome, ...)`, `logAuthLogout(...)` | pure function; emits one structured log entry per call (spec FR-027 / FR-028) |
| `lib/auth/route-guard.tsx` | `RouteGuard` (React function component) | client component; calls `GET /api/v1.0/me` on mount |

Each module is **side-effect-isolated**:
- `lib/auth/password.ts` — only depends on `argon2` and a constant
  for the parameters.
- `lib/auth/session.ts` — only depends on the `redis` singleton
  from `lib/db/redis.ts` (the connection, not the Redis-specific
  shape).
- `lib/auth/cookie.ts` — only depends on `lib/config.ts`.
- `lib/auth/middleware.ts` — composes `lib/auth/session.ts` and
  `lib/auth/cookie.ts`. **No business logic** — the only thing
  the middleware does is read → lookup → attach or `401`.
- `lib/auth/log.ts` — only depends on the application logger.
- `lib/auth/route-guard.tsx` — only depends on
  `lib/api/response.ts` and `lib/auth/log.ts`.

No class-based code in any of these modules except the
typeORM `User` entity (which is mandated by typeORM, per Principle
VI). No service layer, no controller, no DI container.

**Rationale**: the modules match the **functional-first**
posture of Principle VI; each module is independently testable;
the middleware itself is a thin shell that delegates everything
else. The exempt list `PUBLIC_PATHS` is a constant so adding a
new public endpoint is a one-line edit.

**Alternatives considered**:

- **Class-based `AuthService` with `login()` / `logout()` /
  `getSession()` methods** — violates Principle VI (classes only
  where the framework mandates them). Rejected.
- **Single `lib/auth.ts` file with everything inlined** — would
  not match the per-feature module pattern used by 001 / 002
  (`lib/ulid.ts`, `lib/api/*.ts` per file). Rejected on style.

## 11. CORS / CSP / CSRF / XSS posture (cross-references spec + 005)

**Decision**: this feature does **not** introduce the four
Principle IX hardening controls. The cross-cutting propagation
block in the spec and the constitution's Stage 2 In Scope block
both defer those controls to a future `005-security-hardening`
spec. What this feature does ship:

- The auth middleware is **compatible** with the future CSRF
  middleware (it is a separate `withAuth` wrapper, not a
  re-implementation; the future `withCsrf` will compose with it
  via the same `withApiContract` chain).
- The `Secure` cookie flag is environment-driven per Principle IV
  (research §5), which is the one hardening-adjacent concern that
  is in 004's scope.
- The 005 contract already names the three auth endpoints in
  its CSRF exempt list (per the prior session's edit):
  `POST /api/v1.0/login`, `POST /api/v1.0/logout`,
  `GET /api/v1.0/me`.

**Rationale**: spec Clarifications Session 2026-06-21 round 1,
Q1 is unambiguous that 004 ships the auth feature only and 005
ships the four hardening controls. Splitting the work along the
spec boundary keeps each feature small and reviewable.

**Alternatives considered**:

- **Bundling the CSRF token into 004** — would expand 004 into
  004 + half of 005. The spec boundary keeps 004 focused.
  Rejected.

## 12. Testing strategy (resolves spec SC-001..SC-013 + Principle III)

**Decision**: three-tier test suite (inherited from Stage 1):

| Tier | Files | Purpose |
|---|---|---|
| **Unit** | `tests/unit/auth/password.spec.ts` (hash + verify + timing-safe compare), `tests/unit/auth/session.spec.ts` (mocked `ioredis` via `ioredis-mock`), `tests/unit/auth/cookie.spec.ts` (every attribute including the `Secure` env-driven relaxation), `tests/unit/auth/middleware.spec.ts` (401 for missing cookie / unknown session / Redis error; happy path attaches the resolved user), `tests/unit/auth/log.spec.ts` (log-scrub spec — never-leak-secrets per spec SC-012) | pure functions, no DB, no network |
| **Contract** | `tests/contract/auth.api.spec.ts` (full POST/GET/cookie lifecycle against a test Next.js server with an `ioredis-mock` Redis + an in-memory MySQL stub) | HTTP boundary in isolation |
| **Integration** | `tests/integration/auth.spec.ts` (real Redis container + real MySQL container; SC-001..SC-013, including the SC-013 session-fixation pre-seed test, the SC-006 30-minute TTL boundary test, and the SC-005 idempotent-logout test) | end-to-end |

**Rationale**: matches the Stage 1 three-tier pattern (see
`003-backend-api-db/plan.md` §Technical Context → Testing and
`001-teachers/plan.md`). Unit tests cover **every** pure function;
contract tests cover the HTTP boundary (cookie set / clear /
read, status-code mapping); integration tests cover the
**scenario-level** SC-001..SC-013.

**Alternatives considered**:

- **Two-tier (unit + integration only)** — would lose the cookie /
  middleware coverage at the HTTP boundary. Rejected.
- **Adding a `tests/e2e/` Playwright suite** — would cover the
  React route guard end-to-end, but Stage 1 has no Playwright
  setup; adding one is out of Stage 2 scope (Principle V). The
  contract tier covers the route-guard path via a JSDOM-based
  React test that mounts `RouteGuard` and asserts the
  `useRouter().push` call. Documented as a follow-up TODO if a
  future stage wants a real-browser test.

truth** for the authentication boundary (per Principle IV). Every
consumer becomes protected by the same `withAuth` wrapper without
the route handler needing to know about session state. This
matches the spec's "the auth middleware is the single source of
truth for the boundary; route handlers MUST NOT do their own
session lookup" requirement.

## 15. Out-of-scope confirmations (per Constitution Stage Scope)

The following items are **explicitly deferred** (Principle V +
constitution Stage Scope → Stage 2 Out of Scope), and this
feature does **not** introduce them:

- MFA / 2FA.
- OAuth2 / OIDC / SSO.
- Password reset / forgot-password.
- Self-registration / sign-up endpoint.
- Admin authoring of `users` rows (the `npm run seed:admin`
  helper is the only user-creation path).
- Account lockout / brute-force throttling / captcha-after-N.
- Rate limiting beyond Joi input validation.
- Audit logging beyond the existing audit columns (the
  `auth.login` / `auth.logout` structured log entries are
  observability, not a separate `auth_events` table).
- FK migration of `created_by` / `modified_by` on `teachers` /
  `classes` / `subjects` / `levels` to `users.id`.
- COOP / CORP / COEP.

These are documented in the constitution and the spec's
Assumptions block; this research list confirms the per-feature
plan does not introduce them.
