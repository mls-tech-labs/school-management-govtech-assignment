# Private Education Admin Portal

A small admin portal for managing **Teachers** and **Classes** in a private school. Stage 1 ships Create + Read for both entities, backed by Next.js 15 (App Router) + MySQL 8 + typeORM + Joi + Ant Design + Tailwind CSS.

> **Project status**: Stage 1 + Stage 2 implemented. See `specs/001-teachers/`, `specs/002-classes/`, `specs/003-backend-api-db/`, `specs/004-user-auth/`, and `specs/005-security-hardening/` for the source-of-truth specs.

## Quick start (Docker)

```bash
# 1. Copy environment template
cp .env.example .env.local

# 2. Bring up MySQL + Redis (auto-loads docker/mysql/init/01-schema-and-seed.sql
#    on first boot — this is the user-prepared MySQL container per FR-016: the
#    schema, audit columns, ulid CHAR(26) UNIQUE columns, FK constraints, UNIQUE
#    indexes, the subjects / levels reference-list seeds, AND the `users` table
#    are all created by the SQL bootstrap; no typeORM migration runs on app boot)
docker compose -f docker/docker-compose.yml up -d mysql redis

# 3. Bring up the app (no migration step — the app connects to the existing MySQL
#    + Redis). The app refuses to boot without `REDIS_URL` (fail-closed).
docker compose -f docker/docker-compose.yml up -d --build app

# 4. Open the portal — you will be redirected to /login
open http://localhost:3000
```

To wipe and start fresh:

```bash
docker compose -f docker/docker-compose.yml down -v
docker compose -f docker/docker-compose.yml up -d mysql redis   # re-seeds the schema
docker compose -f docker/docker-compose.yml up -d --build app
```

## Seed an admin user (Stage 2 — 004-user-auth)

The `users` table is created by the SQL bootstrap (in
`docker/mysql/init/01-schema-and-seed.sql`); the application does **not**
seed it on boot. To create an admin row:

```bash
# 1. Print a parameterised INSERT — hash + standalone salt are generated by
#    the same argon2id envelope the runtime verifies with (so the seed path
#    and verify path stay in lockstep). The two fields are stored in
#    separate columns (`password` vs `salt`) with independent meanings.
npm run seed:admin -- --username admin --password 'YourP@ssw0rd!' --confirm

# 2. Pipe the printed SQL into your MySQL client:
npm run seed:admin -- --username admin --password 'YourP@ssw0rd!' --confirm \
  | docker exec -i pvt-edu-mysql mysql -uroot -prootpass edu_inst
```

The script refuses to run without `--confirm` (defense against unattended
pipelines, per spec FR-026).

## Log in

1. Open <http://localhost:3000>. Any unauthenticated visit lands on `/login`.
2. Enter the seeded username + password.
3. The browser stores the `pvt_edu_session` cookie (HttpOnly + Secure + SameSite=Strict)
   and the `csrfToken` cookie (SameSite=Strict; used for the double-submit CSRF
   control). Both expire after 30 minutes — no sliding extension.
4. After login, the route guard (`lib/auth/route-guard.tsx`) lets you reach
   `/teachers` and `/classes`.
5. Click **Sign out** in the top-right to clear both cookies and the Redis
   session record.

## Architecture

- **Runtime**: single Next.js 15 process (frontend + API). The Constitution forbids microservice splits.
- **Persistence**: MySQL 8 in a Docker container. The schema, audit columns, `ulid CHAR(26) UNIQUE NOT NULL` row-handle column, FK constraints, UNIQUE indexes, the `subjects` / `levels` reference-list seed data, AND the `users` table are all created by the user against the user-prepared MySQL container (mirrored in `docker/mysql/init/01-schema-and-seed.sql`). The application is read/write at runtime only — `docker compose up` does NOT run any migration step (per FR-016, Session 2026-06-21). The `lib/db/migrations/` directory is out of Stage 1 / Stage 2 scope.
- **Session store**: Redis 7 (separate container). Sessions are `session:<token>` → `{ userId, ulid, createdAt, csrfToken }` with a hard 30-minute TTL. No sliding extension (spec FR-015).
- **Validation**: every request body is validated by Joi before any DB call. Joi schemas mirror the typeORM entity columns field-for-field (Constitution Principle VII).
- **API contract**: every response uses the cross-cutting envelope from `specs/003-backend-api-db/spec.md` (`{ "data": [...] }` for lists, `{ "error": "..." }` for errors, `{ "ulid": "..." }` as the first property on every entry — per FR-021). The Stage 2 status-code table is locked to 400 / 401 / 403 / 404 / 409 / 415 / 500 / 503. All endpoints live under the `/api/v1.0/` version prefix (per FR-022).
- **Authentication boundary** (Stage 2 — 004): every protected `/api/v1.0/*` endpoint (except `POST /api/v1.0/login`, `GET /api/v1.0/me`, `POST /api/v1.0/logout`) goes through `withAuth` → `401 Unauthorized` when no valid `pvt_edu_session` cookie is presented. The session cookie is `HttpOnly` + `Secure` (env-driven, defaults to `NODE_ENV=production`) + `SameSite=Strict`.
- **Hardening** (Stage 2 — 005): every response carries `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and (production only) `Strict-Transport-Security`. Every cross-origin API request is gated by a CORS allow-list. Every state-changing API request (except `POST /api/v1.0/login`, `POST /api/v1.0/logout`, `GET /api/v1.0/me`) is gated by a double-submit CSRF token (constant-time compare).

## Stage 2 assumptions (per the specs)

- **One role**: Authenticated Administrator (per Principle IV).
- **Authentication**: session-based; opaque token in `pvt_edu_session` cookie; Redis-backed with a hard 30-minute TTL (no sliding extension).
- **Authorization**: every `/api/v1.0/*` endpoint except `POST /api/v1.0/login`, `GET /api/v1.0/me`, `POST /api/v1.0/logout` requires a valid session cookie.
- **CSRF**: every state-changing request (except login / logout / `me`) requires a matching `csrfToken` cookie + `X-CSRF-Token` header pair.
- **CORS**: empty allow-list by default (same-origin only); add origins to `CORS_ALLOWED_ORIGINS` for cross-origin access.
- **CSP**: restrictive default (`script-src 'self'`); switch to report-only via `CSP_REPORT_ONLY=true`.
- **HSTS**: enabled by default in production; suppressed in development over HTTP.
- **Stage 2 Out of Scope**: MFA, OAuth/SSO, password reset, self-registration, account lockout, rate limiting beyond Joi, COOP/CORP/COEP.

## Stage 1 assumptions (per the specs)

- **No pagination**: ≤ 500 teachers / classes per stage. Full list returned.
- **Read-only reference lists**: `subjects` (9) and `levels` (10) are seeded once by the user's SQL against the user-prepared MySQL container; admin authoring is a future-stage feature.
- **No edit / delete**: Create + Read only.
- **Phone format**: exactly 8 digits, digits-only, **no leading-digit restriction** (per FR-004, Session 2026-06-21 — the previous Singapore-mobile `^[89]\d{7}$` pattern was removed). Display format on the table is `XXXX XXXX`.
- **Form Teacher control**: searchable combobox over the existing teachers list.

## Validation rules at a glance

- `name` (Teacher): 1..255 chars, required.
- `subject` (Teacher): must match an active entry in `subjects`.
- `email` (Teacher): syntactically valid; **unique across teachers**.
- `contactNumber` (Teacher): exactly 8 digits, digits-only, **no** leading-digit restriction.
- `level` (Class): must match an active entry in `levels`.
- `name` (Class): 1..255 chars; **globally unique**.
- `teacherEmail` (Class): must reference an existing teacher; **unique across classes** (one form teacher per teacher).

## Security hardening (Stage 2 — 005)

Four Principle IX controls are wired at the application boundary:

1. **CORS allow-list** — `middleware.ts` reads `CORS_ALLOWED_ORIGINS` (empty = same-origin only). Preflight from a non-allowed origin → `403` + `{ "error": "cors" }`. Allowed origins see `Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials: true`, and `Vary: Origin` on every response.
2. **CSP header** — `next.config.mjs` emits `Content-Security-Policy` on every response (the restrictive policy from spec FR-003 — `script-src 'self'`, no `unsafe-inline`). Set `CSP_REPORT_ONLY=true` to switch to `Content-Security-Policy-Report-Only` without enforcing.
3. **CSRF double-submit** — `middleware.ts` rejects every state-changing request that does not carry a matching `csrfToken` cookie + `X-CSRF-Token` header pair with `403` + `{ "error": "csrf" }`. Safe methods (`GET` / `HEAD` / `OPTIONS`) and the three auth endpoints bypass. The React fetch wrappers (`app/(private)/teachers/_components/TeacherForm.tsx` + `app/(private)/classes/_components/ClassForm.tsx`) call `getCsrfToken()` from `lib/security/csrf-client.ts` to populate the header.
4. **XSS posture** — layered (Joi input validation + React default output encoding + CSP `script-src 'self'`). No `dangerouslySetInnerHTML` / `eval` / `new Function(…)` anywhere in `app/` (audited by `tests/unit/security/xss-audit.spec.ts`).

Companion headers on every response: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and (production only) `Strict-Transport-Security: max-age=63072000; includeSubDomains`.

### Hardening env keys

| Key | Default | Purpose |
|---|---|---|
| `CORS_ALLOWED_ORIGINS` | empty (same-origin only) | Comma-separated CSV of allowed origins. Empty = fail-closed. |
| `CORS_ALLOWED_HEADERS` | `Content-Type, X-CSRF-Token` | Allowed request headers on preflight. |
| `CSP_POLICY` | the restrictive policy from FR-003 | The CSP value. Override only with full understanding of the trade-off. |
| `CSP_REPORT_ONLY` | `false` | Switches the header name to `…-Report-Only`. |
| `HSTS_ENABLED` | `NODE_ENV === 'production'` | Enables `Strict-Transport-Security` in production. |

See `specs/005-security-hardening/quickstart.md` for the runnable validation scenarios.
