# Private Education Admin Portal

A small admin portal for managing **Teachers** and **Classes** in a private school. Stage 1 ships Create + Read for both entities, backed by Next.js 15 (App Router) + MySQL 8 + typeORM + Joi + Ant Design + Tailwind CSS.

> **Project status**: Stage 1 + Stage 2 + Stage 3 implemented. See `specs/001-teachers/`, `specs/002-classes/`, `specs/003-backend-api-db/`, `specs/004-user-auth/`, `specs/005-security-hardening/`, and `specs/006-teachers-classes-mutations/` for the source-of-truth specs.

## Quick start (Docker)

```bash
# 1. Copy environment template
cp .env.example .env.local

# 2. Bring up MySQL + Redis. On first boot, docker auto-loads
#    docker/mysql/init/01-schema-and-seed.sql — that single file is what
#    creates the schema, audit columns, ulid CHAR(26) UNIQUE columns, FK
#    constraints, UNIQUE indexes, the subjects / levels reference-list
#    seeds, AND the `users` table (per FR-016: no typeORM migration runs on
#    app boot). If you ever need to re-run it manually after the first boot:
#      docker exec -i pvt-edu-mysql mysql -uroot -prootpass edu_inst \
#        < docker/mysql/init/01-schema-and-seed.sql
docker compose -f docker/docker-compose.yml up -d mysql redis

# 3. Seed an admin login user. The script emits an `INSERT INTO users (...)`
#    statement on stdout, hashed with the same argon2id envelope the runtime
#    verifies with (the seed path and verify path stay in lockstep). Pipe the
#    output straight into the MySQL container:
npm run seed:admin -- --username admin --password 'YourP@ssw0rd!' --confirm \
  | docker exec -i pvt-edu-mysql mysql -uroot -prootpass edu_inst

# 4. Bring up the app (no migration step — the app connects to the existing MySQL
#    + Redis). The app refuses to boot without `REDIS_URL` (fail-closed).
docker compose -f docker/docker-compose.yml up -d --build app

# 5. Open the portal — you will be redirected to /login
open http://localhost:3000
```

To wipe and start fresh:

```bash
docker compose -f docker/docker-compose.yml down -v
docker compose -f docker/docker-compose.yml up -d mysql redis   # re-seeds the schema
docker compose -f docker/docker-compose.yml up -d --build app
```

## Seed an admin user

The `users` table is created by the SQL bootstrap (in
`docker/mysql/init/01-schema-and-seed.sql`); the application does **not**
seed it on boot. To create an admin row:

```bash
# 1. Print a parameterised INSERT — hash + standalone salt are generated by
#    the same argon2id envelope the runtime verifies with (so the seed path
#    and verify path stay in lockstep). The two fields are stored in
#    separate columns (`password` vs `salt`) with independent meanings.
npm run seed:admin -- --username admin --password 'YourP@ssw0rd!' --confirm

# 2. Pipe the printed SQL into your MySQL client:
npm run seed:admin -- --username admin --password 'YourP@ssw0rd!' --confirm \
  | docker exec -i pvt-edu-mysql mysql -uroot -prootpass edu_inst
```

The script refuses to run without `--confirm` (defense against unattended
pipelines, per spec FR-026).

## Log in

1. Open <http://localhost:3000>. Any unauthenticated visit lands on `/login`.
2. Enter the seeded username + password.
3. The browser stores the `pvt_edu_session` cookie (HttpOnly + Secure + SameSite=Strict)
   which is configurable with .env file and the `csrfToken` cookie (SameSite=Strict; used
   for the double-submit CSRF control). Both expire after 30 minutes — no sliding extension.
4. After login, the route guard (`lib/auth/route-guard.tsx`) lets you reach
   `/teachers` and `/classes`.
5. Click **Sign out** in the top-right to clear both cookies and the Redis
   session record.

## Architecture

- **Runtime**: single Next.js 15 process (frontend + API). The Constitution forbids microservice splits.
- **Persistence**: MySQL 8 in a Docker container. The schema, audit columns, `ulid CHAR(26) UNIQUE NOT NULL` row-handle column, FK constraints, UNIQUE indexes, the `subjects` / `levels` reference-list seed data, AND the `users` table are all created by the user against the user-prepared MySQL container (mirrored in `docker/mysql/init/01-schema-and-seed.sql`). The application is read/write at runtime only — `docker compose up` does NOT run any migration step (per FR-016, Session 2026-06-21). The `lib/db/migrations/` directory is out of Stage 1 / Stage 2 scope.
- **Session store**: Redis 7 (separate container). Sessions are `session:<token>` → `{ userId, ulid, createdAt, csrfToken }` with a hard 30-minute TTL. No sliding extension (spec FR-015).
- **Validation**: every request body is validated by Joi before any DB call. Joi schemas mirror the typeORM entity columns field-for-field (Constitution Principle VII).
- **API contract**: every response uses the cross-cutting envelope from `specs/003-backend-api-db/spec.md` (`{ "data": [...] }` for lists, `{ "error": "..." }` for errors, `{ "ulid": "..." }` as the first property on every entry — per FR-021). The Stage 2 status-code table is locked to 400 / 401 / 403 / 404 / 409 / 415 / 500 / 503. All endpoints live under the `/api/v1.0/` version prefix (per FR-022).
- **Authentication boundary** (Stage 2 — 004): every protected `/api/v1.0/*` endpoint (except `POST /api/v1.0/login`, `GET /api/v1.0/me`, `POST /api/v1.0/logout`) goes through `withAuth` → `401 Unauthorized` when no valid `pvt_edu_session` cookie is presented. The session cookie is `HttpOnly` + `Secure` (env-driven, defaults to `NODE_ENV=production`) + `SameSite=Strict`.
- **Hardening** (Stage 2 — 005): every response carries `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and (production only) `Strict-Transport-Security`. Every cross-origin API request is gated by a CORS allow-list. Every state-changing API request (except `POST /api/v1.0/login`, `POST /api/v1.0/logout`, `GET /api/v1.0/me`) is gated by a double-submit CSRF token (constant-time compare).

## API contract

The single source of truth is `specs/003-backend-api-db/contracts/common.yaml`. Per-feature contracts inherit from it. The shared security envelope (CORS / CSRF / static headers) lives in `specs/005-security-hardening/contracts/security.yaml`. All endpoints live under the `/api/v1.0/` version prefix (per FR-022, Session 2026-06-21).

Every entity carries the cross-cutting `ulid` row handle (per FR-021) — a 26-character Crockford Base32 string, server-generated by `lib/ulid.ts` via a typeORM `@BeforeInsert()` hook on every entity. Audit columns are hidden (per FR-020). Reference fields are nested `{ ulid, name }` objects on both POST and GET — the server-side lookup is `ulid`-only; the nested `name` is a display hint (echoed back on the response).

### Authentication — `specs/004-user-auth/contracts/auth.yaml`

#### `POST /api/v1.0/login`

Public, CSRF-exempt (the login endpoint establishes the session the CSRF token is bound to).

Request:

```json
{ "username": "admin", "password": "correct horse battery staple" }
```

Success `200` — empty body. Two cookies are set on the response:

```
Set-Cookie: pvt_edu_session=<opaque base64url 43 chars>; Path=/; Max-Age=1800; HttpOnly; Secure; SameSite=Strict
Set-Cookie: csrfToken=<opaque base64url 43 chars>;     Path=/; Max-Age=1800; Secure; SameSite=Strict
```

Use `GET /api/v1.0/me` to fetch the profile. Unknown username, wrong password, and inactive user all return the same `401` body (no enumeration via the error message).

Errors: `400` (`{"error":"\"username\" is required"}` / `{"error":"\"password\" is required"}` / `{"error":"\"rememberMe\" is not allowed"}`), `401` (`{"error":"Invalid username or password"}`), `415`, `500`, `503`.

#### `POST /api/v1.0/logout`

Public, CSRF-exempt, idempotent — runs even when no session is present so the cookie gets cleared.

Success `200` — empty body. Cleared cookie:

```
Set-Cookie: pvt_edu_session=; Path=/; Max-Age=0; Expires=Thu, 01 Jan 1970 00:00:00 GMT; HttpOnly; Secure; SameSite=Strict
```

Errors: `500`.

#### `GET /api/v1.0/me`

CSRF-exempt (safe method). Called by the route guard on every private page mount. The response shape is **exactly** four fields — no `id`, no audit columns.

Success `200`:

```json
{
  "username": "admin",
  "active": true,
  "ulid": "01HZX8K9V4Q7P3WJRN6B5M2YDC",
  "createdAt": "2026-06-21T10:23:45.123456Z"
}
```

Errors: `401` (`{"error":"Unauthorized"}`), `500`, `503`.

#### `GET /api/v1.0/teachers/[ulid]`  *(Stage 3 v2.6.0 — `specs/006-teachers-classes-mutations/contracts/teachers.yaml`)*

Auth: session. CSRF: n/a. The data source for the Edit Teacher RSC page (`/teachers/[ulid]/edit`); the per-row `...` menu's **Edit** item links here.

Success `200`: `Teacher` JSON (same shape as a single `GET /api/v1.0/teachers` entry).

Errors: `400` (`{"error":"Invalid ulid path parameter"}`), `401`, `404` (`{"error":"Teacher not found"}`), `415`, `500`, `503`.

#### `PUT /api/v1.0/teachers/[ulid]`  *(Stage 3 v2.5.0 — `specs/006-teachers-classes-mutations/contracts/teachers.yaml`)*

Auth: session. CSRF: required. Full-resource UPDATE — every mutable field is required. Re-runs every POST-side invariant: subject-active, email-unique with the row-exclusion self-match rule (the same email the row already has is permitted; a collision with a DIFFERENT teacher is rejected), and the Singapore `^[89]\d{7}$` contact-number rule (FR-013 — re-tightened from the relaxed Stage 1 / Stage 2 `^\d{8}$` pattern in `specs/006-teachers-classes-mutations/spec.md` Session 2026-06-22).

Success `200`: the updated `Teacher` JSON with a sibling `previousModifiedAt` field whose value is the row's pre-update `modified_at` ISO-8601 timestamp. The client-side `use-edit-submit` hook compares this to the form-load `modifiedAt`; on a difference it fires the non-blocking antd warning toast `Note: this record was edited by another administrator at HH:MM:SS — your changes are saved, but please verify.` (auto-dismiss after 8 s).

Errors: `400` (Joi — same as POST; Singapore contact-number rejection → `{"error":"Contact number must start with 8 or 9 and be 8 digits."}`; unknown `subject.ulid` → `{"error":"Invalid subject"}`), `401`, `403` (`{"error":"cors"}` / `{"error":"csrf"}`), `404` (`{"error":"Teacher not found"}`), `409` (`{"error":"Email already in use"}`), `415`, `500`, `503`.

#### `DELETE /api/v1.0/teachers/[ulid]`  *(Stage 3 v2.5.0 — `specs/006-teachers-classes-mutations/contracts/teachers.yaml`)*

Auth: session. CSRF: required. Hard delete with the **form-teacher referential integrity guard** (FR-009). On success returns `200` + `{ "ulid": "<deleted-teacher-ulid>" }`. A second DELETE on the same `ulid` (idempotent per Principle X.2) returns `404` silently. The wire envelope on the 409 path uses the singular `details.classUlid` / `details.className` extension (per the one-to-one simplification — `UNIQUE INDEX uq_classes_form_teacher_id` guarantees at most one blocking class; no array, no `… and N more` suffix).

Success `200`: `{ "ulid": "01HZX8K2D5Y3J8QF8W9B3N5P7T" }`.

Errors: `400`, `401`, `403`, `404` (idempotent second DELETE — `{"error":"Teacher not found"}`), `409` (`{"error":"Teacher is assigned as form teacher of class \"<className>\". Reassign or delete that class first.", "details": { "classUlid": "<ulid>", "className": "<name>" }}`), `415`, `500`, `503`.

Auth: session. CSRF: required. Full-resource UPDATE — every mutable field is required. Success `200`: the updated `Class` JSON with a sibling `previousModifiedAt` field (same concurrent-edit toast semantics as PUT-Teacher).

Errors: `400` (Joi; unknown `level.ulid` → `{"error":"Invalid level"}`), `401`, `403`, `404` (`{"error":"Class not found"}` / `{"error":"Teacher not found"}`), `409` (`{"error":"Class name already in use"}` / `{"error":"Teacher already assigned"}`), `415`, `500`, `503`.

#### `DELETE /api/v1.0/classes/[ulid]`  *(Stage 3 v2.5.0 — `specs/006-teachers-classes-mutations/contracts/classes.yaml`)*

Auth: session. CSRF: required. Hard delete with **no referential-integrity check** (per FR-010 / Principle X.2 — no other table references `classes.id` outside the audit columns). On success returns `200` + `{ "ulid": "<deleted-class-ulid>" }`. A second DELETE on the same `ulid` returns `404` silently (Principle X.2). After a successful delete, the teacher who was the deleted class's form teacher is eligible to be the form teacher of a new class (the form-teacher uniqueness invariant is freed by the class delete).

Success `200`: `{ "ulid": "01HZX8K2D5Y3J8QF8W9B3N5P7T" }`.

Errors: `400`, `401`, `403`, `404` (idempotent second DELETE — `{"error":"Class not found"}`), `415`, `500`, `503`. No `409` path.

### Validation rule changes (FR-013)

The Singapore contact-number rule is **re-tightened** to `^[89]\d{7}$` on both POST and PUT paths. The relaxed `^\d{8}$` pattern from the Stage 1 / Stage 2 window is gone. Leading digits `0`–`7` and 10+ are rejected with the field-level error `Contact number must start with 8 or 9 and be 8 digits.`. This rule is enforced by the shared `lib/validation/contact-number.ts` module (used by both `lib/validation/teacher.ts` and any future consumer) — the wire field `contactNumber` is validated against the canonical regex on every write.

## Security hardening (Stage 2 — 005)

Four Principle IX controls are wired at the application boundary:

1. **CORS allow-list** — `middleware.ts` reads `CORS_ALLOWED_ORIGINS` (empty = same-origin only). Preflight from a non-allowed origin → `403` + `{ "error": "cors" }`. Allowed origins see `Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials: true`, and `Vary: Origin` on every response.
2. **CSP header** — `next.config.mjs` emits `Content-Security-Policy` on every response (the restrictive policy from spec FR-003 — `script-src 'self'`, no `unsafe-inline`). Set `CSP_REPORT_ONLY=true` to switch to `Content-Security-Policy-Report-Only` without enforcing.
3. **CSRF double-submit** — `middleware.ts` rejects every state-changing request that does not carry a matching `csrfToken` cookie + `X-CSRF-Token` header pair with `403` + `{ "error": "csrf" }`. Safe methods (`GET` / `HEAD` / `OPTIONS`) and the three auth endpoints bypass. The React fetch wrappers (`app/(private)/teachers/_components/TeacherForm.tsx` + `app/(private)/classes/_components/ClassForm.tsx`) call `getCsrfToken()` from `lib/security/csrf-client.ts` to populate the header.
4. **XSS posture** — layered (Joi input validation + React default output encoding + CSP `script-src 'self'`). No `dangerouslySetInnerHTML` / `eval` / `new Function(…)` anywhere in `app/` (audited by `tests/unit/security/xss-audit.spec.ts`).

Companion headers on every response: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and (production only) `Strict-Transport-Security: max-age=63072000; includeSubDomains`.

### Hardening env keys

| Key | Default | Purpose |
|---|---|---|
| `CORS_ALLOWED_ORIGINS` | empty (same-origin only) | Comma-separated CSV of allowed origins. Empty = fail-closed. |
| `CORS_ALLOWED_HEADERS` | `Content-Type, X-CSRF-Token` | Allowed request headers on preflight. |
| `CSP_POLICY` | the restrictive policy from FR-003 | The CSP value. Override only with full understanding of the trade-off. |
| `CSP_REPORT_ONLY` | `false` | Switches the header name to `…-Report-Only`. |
| `HSTS_ENABLED` | `NODE_ENV === 'production'` | Enables `Strict-Transport-Security` in production. |

See `specs/005-security-hardening/quickstart.md` for the runnable validation scenarios.
